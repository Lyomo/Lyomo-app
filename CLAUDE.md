# LÖMO — контекст для агента

## О проекте
Соц-сеть с чатом: Express + SQLite (встроенный `node:sqlite`, без внешних
npm-зависимостей для БД) + WebSocket на backend, мультистраничный vanilla
JS/HTML/CSS на frontend (без сборщика, без TS, без тестов).
Требуется Node.js >= 22.5 (модуль `node:sqlite`); разрабатывалось и
протестировано на Node 24 LTS.

## Стек и структура
- `server.js` — весь backend в одном файле: Express REST + `WebSocketServer`
  (чат, история сообщений хранится в SQLite, лимит 50 последних на комнату).
  Все `/api/*`-маршруты, кроме `/api/register` и `/api/login`, защищены
  `requireAuth` (JWT в заголовке `Authorization: Bearer`).
  Загруженные файлы раздаются отдельным статическим маршрутом `/uploads`
  (папка `process.env.UPLOADS_DIR`, по умолчанию `./uploads`) — НЕ через
  `PUBLIC_FILES`-allowlist, который отдаёт только конкретный список HTML/CSS/
  JS-файлов (важно: если добавляешь новую HTML-страницу — её имя нужно
  вписать в `PUBLIC_FILES`, иначе она будет 404-иться). Этот `/uploads`-роут
  зарегистрирован РАНЬШЕ корневого `express.static(cwd)` — так и должно
  быть, иначе корневая статика сама находит файлы в `uploads/` (это реальная
  подпапка проекта) и отдаёт их в обход заголовков безопасности ниже.
  `POST /api/upload` — общий загрузчик (фото к посту, файл в чат): картинки
  отдаются инлайн, всё остальное — с `Content-Disposition: attachment`
  (чтобы .html/.svg с чужим скриптом не выполнился в контексте нашего
  origin), плюс блок-лист опасных расширений на входе (`DANGEROUS_EXT`).
  Имя файла из `req.file.originalname` ВСЕГДА пропускай через
  `fixFilenameEncoding()` перед сохранением/ответом — busboy по умолчанию
  декодирует не-ASCII имена (кириллицу и т.д.) как latin1, без этого
  получаются кракозябры.
- **`login` vs `displayName`**: `login` — фиксированный технический
  идентификатор (уникальность, вход, WS-подключение, `dm-`-комнаты кодируются
  по ID, не по login) и НИГДЕ не редактируется через UI. `displayName` —
  то, что реально видят другие пользователи (посты, комментарии, друзья,
  чат) и что можно поменять на "Мой аккаунт". Раньше на аккаунте было поле
  "Как тебя зовут?", которое меняло имя ТОЛЬКО в localStorage самого
  пользователя — нигде больше не отражалось, отсюда путаница. Теперь это
  настоящее поле `users.displayName`, обновляется через `PATCH /api/me`,
  и `displayNameOf(user)` в `server.js` — общая точка, откуда оно
  подставляется в `authorName` постов/комментариев и `toPublicUser`.
  `login` также больше НЕ показывается в UI (`account.html`/`profile.html`) —
  публично виден только `displayName` и ID; сам логин по-прежнему приходит
  в ответах `/api/me` и `/api/user-by-id/:id` (нужен клиенту для WS и
  внутренней логики), просто не рендерится на экран.
- **ID пользователя** — с этого захода короткий: 6 цифр + 2 заглавные буквы
  (например `771833RN`), генерируется `generateUserId()` в `server.js`
  (проверяет уникальность через `stmts.findUserById`, до 50 попыток).
  Раньше был `crypto.randomUUID()`. Существующие на момент смены формата
  аккаунты (admin/visual_test/visual_test2) были миграцией переведены на
  новый формат одноразовым скриптом — ID пересчитан и везде корректно
  перепривязан (`posts.ownerId/authorId`, `likes.userId`,
  `comments.authorId`, `friendships.userA/userB/requestedBy` — с
  восстановлением порядка `userA < userB`, `groups.ownerId`,
  `group_members.userId`, `albums.ownerId`, `photos.ownerId`,
  `stories.ownerId`); все, кто был залогинен на момент миграции, были
  разлогинены (старый ID в JWT переставал существовать в БД). Скрипт был
  одноразовым и удалён — если понадобится мигрировать ID снова (например,
  после ручной правки БД), писать по тому же принципу: пройтись по всем
  таблицам с `ownerId`/`authorId`/`userId`, заменить в транзакции, `users.id`
  обновлять последним.
- `db.js` — подключение к SQLite (файл по пути `process.env.DB_PATH`,
  по умолчанию `./data/lomo.db`). Таблицы: `users` (+`about`, +`displayName`
  — оба раньше жили только в localStorage и не были видны другим, теперь
  настоящие поля, обновляются через `PATCH /api/me`), `messages`
  (+`fileUrl`/`fileName` — вложение к сообщению чата; `avatar` и
  `fromDisplayName` — снимок аватара/имени отправителя НА МОМЕНТ отправки,
  не обновляются задним числом у старых сообщений при смене профиля), `posts` (стена —
  `ownerType` `'user'`|`'group'` + `ownerId`, общая для профилей и групп;
  +`photoUrl` — фото к посту, рендерится ДО текста), `likes`, `comments`
  (+`photoUrl` — фото к комментарию, рендерится ПОСЛЕ текста, то есть в
  обратном посту порядке — так и задумано), `friendships` (пара id хранится
  как `userA < userB`, см. `friendPair()` в `server.js`), `groups`,
  `group_members`, `albums`, `photos`, `stories` (сторис на Главной, живут
  24 часа — см. `STORY_TTL_MS`, чистятся лениво при каждом `GET /api/stories`,
  без крона). Новые колонки в уже существующие таблицы добавляются безопасно
  через `ensureColumn()` (аддитивный `ALTER TABLE ADD COLUMN`, ничего не
  удаляет) — паттерн для будущих миграций. `node:sqlite` принимает только
  позиционные `?`-параметры — НЕ `@name`/`:name` (лишний ключ в объекте
  кидает `Unknown named parameter`).
- `app.js` — вся клиентская логика и роутинг по имени текущего HTML-файла
  (index.html, account.html, auth.html, chats.html, users.html, admin.html,
  groups.html, group.html, profile.html, friends.html, photos.html,
  music.html, video.html, books.html). Общий рендер стены — функция
  `initWall()`, переиспользуется на account.html/profile.html/group.html.
  `index.html` (Главная) — НЕ профиль, это лента: сторис-ряд
  (`initStoriesRow()`) + агрегированная лента публикаций (`renderFeed()` →
  `GET /api/feed` — свои посты + посты друзей + посты групп, где состоишь).
  Личный профиль/редактирование/своя стена — на `account.html`
  (`initAccountPage()`, бывшая `initHomePage()`).
- Стили — `styles.css`, без препроцессоров. Визуально всё ещё в текущем
  «стеклянном» стиле — полноценный ретро-скин под ВК 2010 (шрифты, цвета
  страницы целиком) по-прежнему не делали; сделали только структурную часть
  «как в ВК 2010» — сторис + лента вместо профиля на Главной.
- **Иконки** — везде инлайн-SVG вместо эмодзи. Набор путей и хелпер
  `icon(name, size)` объявлены в `components.js` (`ICON_PATHS`) и доступны
  из `app.js` без импорта — оба подключены обычными `<script>` без
  `type="module"`, поэтому top-level `const`/`function` из components.js
  видны в app.js (один script scope документа; `components.js` должен
  грузиться ПЕРВЫМ). Используется и в меню (`renderMenu()`/`renderHeader()`
  в components.js), и в действиях (лайк/комментарий/прикрепить/удалить/
  отправить и т.д. в app.js). Добавляя новую иконку — впиши путь в
  `ICON_PATHS`, только `stroke`, без лишних `fill` (кроме треугольника play
  в `video` — там осознанно `fill="currentColor" stroke="none"` на самом
  `<path>`, это единственное исключение).
- **Мобильная адаптация** — сайдбар на экранах `≤768px`
  (`@media (max-width:768px)` в конце `styles.css`) превращается в
  выезжающую слева панель (`position:fixed`, `transform:translateX(-100%)`
  → `.sidebar.open{transform:translateX(0)}`) поверх контента, с
  затемняющей подложкой `.sidebar-backdrop` и кнопкой-бутербродом
  `#menuToggleBtn` в шапке (видна только на мобильном). Вся логика
  открытия/закрытия — `initMobileMenu()` в app.js, вызывается БЕЗУСЛОВНО
  первой строкой в `DOMContentLoaded` (до проверки залогинен ли юзер),
  потому что должна работать и на `auth.html` тоже. `auth.html` не грузит
  `components.js` (у него нет полноценного меню) — бутерброд/крестик/луна
  там захардкожены статикой прямо в HTML теми же SVG-путями, что и в
  `ICON_PATHS`; если поменяешь путь иконки в `ICON_PATHS` — обнови и
  `auth.html` вручную, они не связаны программно.

## Известные проблемы, приоритет исправления

1. **[РЕШЕНО, но нужно ручное действие] Раньше в `server.js` был захардкожен
   реальный логин/пароль от MongoDB Atlas как fallback-значение `MONGO_URI`.**
   Теперь БД — локальный файл SQLite (`db.js`, путь через `.env` → `DB_PATH`),
   MongoDB и Atlas в проекте больше не используются.
   - **старый пароль пользователя БД в MongoDB Atlas всё ещё стоит сменить/
     удалить вручную — он раньше был закоммичен в открытом виде, агент не
     может сделать это сам, обязательно напомни об этом человеку**
   - на VPS файл `data/lomo.db` — это единственный источник данных, у него
     нет автоматических бэкапов, как у managed-БД; нужно резервное копирование
     этого файла вручную/по крону

2. **[РЕШЕНО]** Пароли хешируются через встроенный `crypto.scrypt`
   (`hashPassword`/`verifyPassword` в `server.js`, формат колонки —
   `"соль:хеш"`, обе части hex). Не bcrypt/argon2 намеренно — это нативные
   npm-модули, а на этой машине уже был случай, когда нативный модуль
   (`better-sqlite3`) не собрался без Visual Studio Build Tools; scrypt
   встроен в Node и даёт тот же уровень стойкости. При старте сервера
   одноразово мигрирует старые открытые пароли в хеш (`migratePlaintextPasswords`
   в `server.js`, определяет по regex — если значение не похоже на
   `"соль:хеш"`, значит ещё не хешировано).

3. **[ЧАСТИЧНО РЕШЕНО] REST защищён JWT, WebSocket — нет.** REST-маршруты
   (кроме register/login) проверяют `Authorization: Bearer` через
   `requireAuth`. Но WS-подключение (`connectWebSocket()` в `app.js`) всё ещё
   передаёт `login` как query-параметр без токена — сервер верит ему на слово,
   значит теоретически можно подключиться и слать сообщения от чужого имени.
   Нужно: передавать и проверять JWT при установке WS-соединения тоже.

4. **[РЕШЕНО]** `GET /api/user-by-id/:id` реализован в `server.js` —
   поиск диалога по ID в чате и просмотр чужого профиля (`profile.html`)
   работают.

5. **[РЕШЕНО]** Старый `admin.js` (мёртвый localStorage-конфиг
   `mychat_admin_v1`, нигде не читался) удалён вместе со ссылкой на него из
   `PUBLIC_FILES`. `admin.html`/`users.html` теперь настоящая админка — см.
   раздел «Админка» ниже.

6. **[ЧАСТИЧНО РЕШЕНО, осознанный компромисс] `admin.html`/`users.html` сами
   HTML-страницы по-прежнему отдаются любому по прямой ссылке** (они в
   `PUBLIC_FILES`, как и остальные страницы), но это уже не проблема
   безопасности: весь функционал внутри них работает через `/api/admin/*`,
   а туда пускает только `requireAuth` + `requireAdmin` (проверяет
   `req.user.isAdmin` из БД на каждый запрос). Не-админ откроет пустые
   страницы — данные всё равно не подтянутся. Пункт навигации на «Админ»/
   «Пользователи» тоже скрыт на клиенте для не-админов, как и раньше.

## Соц-фичи (стена, друзья, группы, фото) — сознательные упрощения

Реализовано: стена профиля/группы (посты, лайки, комментарии, опционально
фото к посту), друзья (заявки/подтверждение, одна строка поиска — логин ИЛИ
точный ID через `GET /api/users?q=`, см. `searchUsers` в `server.js`),
реальные группы (создание, вступление, выход, владелец не может выйти без
удаления группы), фотоальбомы с загрузкой файлов через `multer` (только
`image/*`, лимит 8MB — отдельно от общего `/api/upload`), чат с вложением
файла (любой не-опасный тип, лимит 20MB, картинки рендерятся инлайн,
остальное — ссылкой на скачивание).

Сознательно НЕ сделано в этом заходе (не баги, а осознанные границы MVP):
- Стены **публичные** — читать может любой залогиненный пользователь, без
  проверки дружбы.
- Постить можно только **на свою стену** (или на стену группы, если ты
  участник) — писать на чужой профиль нельзя.
- Нет уведомлений (о заявке в друзья, лайке, комментарии) — только то, что
  видно при заходе на страницу.
- Нет пагинации нигде (посты, комментарии, друзья, группы, фото) — ок при
  игрушечном объёме данных, но всё грузится целиком.
- При удалении группы (`DELETE /api/groups/:id`) посты этой группы удаляются,
  но их лайки/комментарии — нет (остаются висеть в БД как мусор, на
  функциональность не влияет).
- У групп аватар — только URL-строка (как у пользователя), а не файл, в
  отличие от фотоальбомов.

## Админка (`admin.html`, `users.html`)

Реализована по мотивам обычных соц-сетей: обзор-статистика, модерация
публикаций/групп, управление пользователями. Всё под `requireAuth,
requireAdmin` в `server.js`.

- `users.users.isBanned` (0/1) и `users.createdAt` — новые колонки через
  `ensureColumn()`.
- **`requireAuth` теперь бьёт в БД на КАЖДЫЙ запрос** (`stmts.findUserById`),
  а не доверяет только полю из JWT — из-за этого бан/разбан и выдача/снятие
  прав админа применяются мгновенно, без ожидания истечения токена (7 дней).
  То же самое на подключении к WS: `connectingUser.isBanned` проверяется до
  `ws.close(4003, "banned")`. `POST /api/login` тоже проверяет `isBanned` и
  отвечает 403.
- `GET /api/admin/stats` — счётчики (пользователи/админы/забаненные/посты/
  комментарии/сообщения/группы/фото/сторис).
- `GET /api/admin/users?q=` — поиск по логину, `toAdminUser()` (расширяет
  `toPublicUser` полями `isAdmin`/`isBanned`/`createdAt`).
- `PATCH /api/admin/users/:id` — переключает `isAdmin`/`isBanned`; блокирует
  снятие прав/бан самого себя (отдельные сообщения об ошибке на каждый
  случай, кнопки в `users.html` для своей строки тоже задизейблены на клиенте
  с тултипом — двойная защита).
- `DELETE /api/admin/users/:id` — полное каскадное удаление: свои группы
  удаляются целиком (с постами/лайками/комментариями/фото), собственные
  посты/комментарии/лайки/фотоальбомы/сторис/дружбы/членства в группах —
  тоже; файлы фото удаляются с диска. Себя удалить нельзя.
- `GET /api/admin/posts?q=` — полнотекстовый поиск по всем постам (любой
  стены), с `contextLabel`. `GET /api/admin/groups` — все группы.
- `DELETE /api/comments/:id` — новый роут (автор либо админ). Удаление
  поста/фото/сторис теперь тоже пропускает владельца ИЛИ админа
  (`req.user.isAdmin` в условии).
- Фронтенд: `initAdminPage()`/`initUsersPage()` в `app.js`, роутинг по
  `path.endsWith("admin.html"/"users.html")`. Кнопка модерации на карточке
  поста переиспользует существующий `renderPostCard()` — просто добавляет
  одну кнопку в `.post-actions`.

## Автомодерация (`moderation.js`)

Локальный офлайн-фильтр (без внешних AI-сервисов и API-ключей — осознанный
выбор пользователя между "просто и бесплатно" и "платно через Claude API";
если позже понадобится реально понимать смысл текста/картинок — это будет
отдельный, более дорогой заход). НЕ анализирует смысл — сопоставляет с
паттернами. Две независимые проверки:

- **Текст** — `moderateText(text)` в `moderation.js`, вызывается в
  `POST /api/posts` и `POST /api/posts/:id/comments` перед вставкой в БД.
  Нормализует текст ПОСЛОВНО (leet-замены цифрами, латиница вместо похожей
  кириллицы, разделители типа "с.у.к.а") — специально не схлопывает весь
  текст в одну строку, чтобы не склеивать соседние слова и не плодить
  ложные срабатывания. Считает score по корням слов (не полным словам —
  ловит склонения) + эвристикам (капс, спам-ссылки, повторы символов).
  `score >= 80` → **reject** (публикация блокируется сразу, 400 с причиной,
  ничего не пишется в БД). `score 30-79` → **flag** (публикуется, но
  `moderationStatus='flagged'` — скрыта из ленты/стены/комментариев для
  всех, кроме автора и админа, см. `filterVisible()` в server.js, до
  ручного решения в админке). `< 30` → clean, как обычно.
  Корни для "разжигания" (`GROUP_ROOTS`+`THREAT_ROOTS`, совпадение обоих
  в одном тексте) — эвристика на случай, когда явного мата нет, но по
  совокупности похоже на угрозу в адрес группы людей (мотивирующий кейс:
  "Евреи пожалеют о содеянном, все они виноваты" — ловится этой эвристикой,
  НЕ словарём мата). Корни держи короткими из-за "плавающих" гласных в
  русском склонении (хохол/хохлы) — иначе легко словить ложные срабатывания
  (`хохо` как корень ловил бы и "хохотать").
- **Картинки** — `isRealImage(buffer)` в `moderation.js`, проверяет
  сигнатуру первых байт файла (JPEG/PNG/GIF/WEBP), вызывается в
  `POST /api/upload` и `POST /api/albums/:albumId/photos` ПОСЛЕ того, как
  multer уже записал файл на диск (`rejectIfFakeImage()` в server.js читает
  16 байт, удаляет файл при несовпадении). Ловит только случай "файл выдаёт
  себя за картинку, а на самом деле не картинка" (подмена mimetype) — само
  содержимое картинки (что на ней) НЕ анализируется, это по-прежнему
  недоступно офлайн без внешнего сервиса.

Схема: `posts`/`comments` получили колонки `moderationStatus` ('clean' по
умолчанию | 'flagged') и `moderationReason` (text). Админка
(`admin.html` → секция «На проверке») дёргает `GET /api/admin/moderation`
(отдаёт весь список flagged) и одобряет через `PATCH
/api/admin/posts/:id/approve` / `PATCH /api/admin/comments/:id/approve`
(сбрасывает статус в 'clean'); удаление — существующими `DELETE`-роутами.

**Важно про `[hidden]`**: на `.moderation-reason` НЕ ставь свойство
`display` в CSS — это тот же баг, что уже ловили в сессии на `#preview`:
author-стиль с `display` всегда бьёт UA-правило `[hidden]{display:none}`,
и пустой блок остаётся видимым (8px пустоты) даже с атрибутом `hidden`.
Используй `width: fit-content` вместо `display: inline-block`, если нужен
блок по ширине контента.

## Мобильная адаптация (продолжение)

`users.html` — таблица не влезала по ширине на `≤768px` (кнопки действий
обрезались до нечитаемых огрызков типа "Сд", "Заб"). Фикс — классический
"responsive table": в мобильном `@media` блоке `table/tbody/tr/td`
получают `display:block`, `thead` скрыт, `td[data-label]::before`
подставляет подпись поля через CSS `content: attr(data-label)`. `data-label`
проставляется в JS (`initUsersPage()` в app.js) только на ячейки
логина/статуса — у ячейки "Пользователь" (аватар+имя) и "Действия"
(кнопки) подписи не нужны, они самоочевидны. Если добавляешь новую колонку
в эту таблицу — не забудь `data-label`, иначе на мобильном у неё не будет
подписи поля.

**Скролл в выезжающем мобильном меню.** Раньше скроллился весь `.sidebar`
целиком — на невысоких экранах (или когда залогинен админ и в меню
добавляются "Админ"/"Пользователи") шапка с крестиком закрытия и кнопка
"Выйти" уезжали вместе с контентом за пределы экрана и становились
недостижимы без скролла назад. Исправлено разделением на три flex-блока
внутри `.sidebar` (`display:flex;flex-direction:column`):
`.sidebar-top` (лого+крестик) и `.logout-btn` — `flex:0 0 auto`,
зафиксированы; между ними `.sidebar-scroll` (обёртка вокруг `.nav-list` +
ссылок "Админ"/"Пользователи", добавлена в `renderMenu()` в
components.js) — `flex:1 1 auto; overflow-y:auto`, скроллится только он.
Работает только в мобильном `@media`-блоке — на десктопе `.sidebar` не
скроллится вовсе (всё и так помещается), `.sidebar-scroll` там обычный
блок без `overflow`. Тонкий скроллбар для `.sidebar-scroll` — тот же
паттерн, что у `.log`/`#roomList` (секция "SCROLLBARS" в styles.css).

**Регрессия от этого же фикса (важно на будущее).** Изначально
`min-height: 0` на `.sidebar-scroll` был в БАЗОВОМ (не мобильном) правиле.
На десктопе, если окно невысокое (админ залогинен → сайдбар длиннее
окна), это давало flex-shrink право сжать `.sidebar-scroll` НИЖЕ высоты
его реального контента (у flex-item `min-height` по умолчанию `auto` =
"не меньше контента", `min-height:0` явно снимает эту защиту) — сам блок
сжимался, а его дети (nav-admin/nav-users) вылезали за пределы уже
сжатого блока и налезали на "Выйти", который позиционировался по краю
сжатого (а не настоящего) блока. Итог — пункты меню накладывались друг на
друга. Фикс: `min-height: 0` должен быть ТОЛЬКО внутри мобильного
`@media`-блока (он там обязателен — без него `flex:1 1 auto` +
`overflow-y:auto` не сработает, т.к. блоку не разрешат сжаться под
скролл), на десктопе `.sidebar-scroll` не должен его иметь вообще.
Общий урок: `min-height: 0` на flex/grid-item — всегда обдуманно решай,
для какого именно breakpoint'а он нужен, не добавляй "на всякий случай"
в базовое правило.

**Скролл сайдбара на десктопе.** После фикса выше пункты меню на
десктопе перестали накладываться друг на друга, но на невысоком окне
(особенно с "Админ"/"Пользователи" для админа) низ списка всё ещё
обрезался viewport'ом без возможности докрутить — на десктопе `.sidebar`
не выезжающая панель, просто узкая колонка слева, и раньше у неё не
было `overflow`. Добавлено `overflow-y: auto` прямо в БАЗОВОЕ правило
`.sidebar` (styles.css, самое начало) — работает только когда контент
реально не помещается (обычно не видно, скроллбар не мешает). В мобильном
`@media`-блоке это перекрывается обратно в `overflow: hidden`, т.к. там
скроллится внутренний `.sidebar-scroll`, а не сам `.sidebar` (см. выше) —
если меняешь `.sidebar` overflow, не забывай про этот override ниже по
файлу. Тонкий скроллбар — та же секция "SCROLLBARS", `.sidebar` добавлен
туда третьим селектором рядом с `.sidebar-scroll`.

**Резкая граница фона на коротких мобильных страницах.** `body` красится
радиальными градиентами, угасающими к центру ("45%"), привязанными к
своим же верхнему левому/нижнему правому углу. На мобильном `body` —
`height:auto` (для обычного скролла страницы вместо десктопного
`overflow:hidden` с внутренним скроллом `.app`), поэтому на странице с
малым количеством контента (мало постов и т.п.) блок `body` короче
экрана — градиент угасает в пределах своих ~400px, ниже видна только
плоская заливка `var(--bg)`, и получается резкая горизонтальная граница
посередине экрана. Исправлено — `body { min-height: 100vh; min-height:
100dvh; }` внутри мобильного `@media`-блока, чтобы фон всегда был минимум
на весь экран независимо от длины контента (для контента ДЛИННЕЕ экрана
ничего не меняется — `height:auto` всё так же даёт странице расти дальше
и скроллиться).

## Друзья (`friends.html`) — вкладки + подписки

Поиск теперь один блок сверху страницы (без заголовка "Найти человека"),
под ним вкладки: **Друзья** / **Заявки** (бывшие "Входящие заявки") /
**Подписки**. Переключение вкладок — чисто клиентское (`initFriendsPage()`
в app.js: `.tab-btn` клик прячет/показывает соответствующий `<div
id="friends...List">` через атрибут `hidden`; данные для всех трёх вкладок
подгружаются сразу при заходе на страницу, не лениво по клику).

**Подписки** = мои исходящие заявки в друзья, которые ещё не приняты
(`friendships.status='pending' AND requestedBy=я`) — семантика "я
подписан, но не факт что взаимно", как в ВК 2010. Новый роут `GET
/api/friends/subscriptions` + `stmts.listOutgoingRequests` в server.js
(зеркало уже существовавшего `listIncomingRequests`, но
`f.requestedBy = ?` вместо `<>`). Отписаться = тот же `POST
/api/friends/decline/:userId`, что уже использовался для отклонения
входящей заявки и удаления друга — он просто удаляет строку `friendships`
независимо от направления, поэтому отдельный роут не понадобился.
Технически подписка не даёт никакого отдельного доступа к контенту —
стены и так публичны для любого залогиненного (см. пункт выше про
сознательные упрощения) — это просто список "кого я хочу видеть в
друзьях, но пока в одну сторону", а не механизм контроля доступа.
Блокировки пользователей (чтобы подписка/видимость реально что-то
ограничивала) в проекте нет — если понадобится, это отдельная фича
(таблица `blocks`, проверка в `requireAuth`/при рендере стены).

**Важно про `[hidden]`**: после того, как на эту же грабли наступили уже
трижды (`#preview`, `.moderation-reason`, теперь `.person-list` с
`display:flex`), добавлено глобальное защитное правило `[hidden] {
display: none !important; }` в начале styles.css. Теперь НЕ нужно
подбирать `width:fit-content` вместо `display` для новых элементов,
которые прячутся через `hidden`, — правило само гарантирует, что `hidden`
побеждает любой `display` от класса. Если увидишь элемент с `hidden`,
который всё равно видим, — это правило либо отсутствует, либо
переопределено более специфичным/поздним `!important`-правилом.

## Чаты (`chats.html`) — список диалогов в стиле ВК

По референсам (скриншоты старого ВК-десктопа + мобильного клиента):
сначала выбираешь диалог из списка, потом переписываешься внутри него.

- **Список диалогов** (`renderRoomsList()` в app.js) — теперь не просто
  текст, а строка `.room-item`: аватар (`.room-avatar`, фото или первая
  буква названия), имя + превью последнего сообщения (`.room-preview` —
  "Вы: текст" если последнее сообщение моё, иначе просто текст; "Вложение"
  если это файл без текста), время справа (`.room-time` —
  `formatRoomTime()`: часы:минуты если сегодня, иначе "3 июл"). Данные
  берутся из уже существующего локального кэша сообщений
  (`loadMessages(roomId)` — последний элемент массива), новых полей в БД
  не добавлялось. Превью обновляется на КАЖДОЕ сообщение (не только для
  новых комнат) — `renderRoomsList()` теперь вызывается безусловно в WS
  `message`-хендлере (server.js тут ни при чём, это чисто клиентский кэш).
- **Мобильный полноэкранный режим** — на `≤768px` список и сам чат больше
  не стоят друг под другом (как было раньше), а показываются по одному,
  как два "экрана": класс `.chat-open` на `.chat-layout` переключает
  видимость (`renderRoomsList()` добавляет класс по клику на диалог,
  `#chatBackBtn` — кнопка со стрелкой в шапке чата, видна только на
  мобильном — его убирает). На десктопе класс `.chat-open` ничего не
  меняет, обе колонки всегда видны рядом (grid, как раньше).
- Порядок при открытии страницы: `.chat-open` не выставлен по умолчанию —
  на мобильном всегда сначала виден список (как на референсе), даже
  если `currentRoom`/сообщения уже отрендерены в фоне в скрытый
  `.chat-main`.
- **Создание комнаты — БЕЗ `prompt()`.** Раньше "+ Комната" вызывала
  нативный `window.prompt()` — в части окружений/браузеров такие
  диалоги вообще не показываются (тихо возвращают `null`), кнопка
  выглядела нерабочей. Теперь по клику раскрывается обычная инлайн-форма
  (`#addRoomForm`, input + "Создать") под кнопкой — тот же паттерн, что
  везде в проекте (создание группы/альбома). На мобильном после создания
  комнаты `.chat-open` выставляется автоматически, как и при клике на
  диалог в списке. **Урок**: в этом проекте НЕ используй `alert`/`confirm`/
  `prompt` для чего-либо важнее одноразового уведомления — они не
  тестируются автоматизацией (см. более ранние заметки про `confirm()`
  при удалении) и могут быть недоступны части реальных пользователей;
  всегда инлайн-форма или кастомный тост/баннер (`confirm()` для
  подтверждения ОПАСНОГО действия типа удаления — это ок и так уже
  сделано во всём проекте, эта рекомендация конкретно про `prompt()`
  для ввода данных).

**Шапка чата — счётчик "в сети" и меню-троеточие (как в телеграме).**
- `broadcastPresence(room)` в server.js — считает реальное число РАЗНЫХ
  логинов, сейчас подключённых к комнате (`clients` Set, WS), и шлёт всем
  в этой комнате `{type:"presence", room, count}` при каждом
  подключении/отключении кого-либо. Это НЕ "участники беседы" в смысле
  членства — такой сущности в модели чата нет (комната это просто строка,
  подключиться может кто угодно, знающий её id) — а честный live-счётчик
  "сколько человек прямо сейчас смотрит в этот чат". Клиент:
  `updateRoomPresence(count)` в app.js пишет "N в сети" в
  `#chatHeaderSubtitle`, вызывается из WS-хендлера на `msg.type ===
  "presence"`, только если `msg.room === currentRoom`. `setStatusOnline()`
  теперь дёргается только при обрыве соединения (пишет "нет соединения") —
  при удачном коннекте текст не трогает, ждёт presence, чтобы не мелькала
  неточная надпись перед реальным числом.
- Кнопка `#chatMenuBtn` (иконка `moreVertical`) открывает
  `#chatMenuDropdown` — содержимое СОБИРАЕТСЯ ДИНАМИЧЕСКИ в
  `renderChatMenu()` (app.js), вызывается из `updateChatHeader()` при
  каждой смене чата, т.к. набор пунктов разный для комнаты/группы и для
  личного диалога (`currentRoom.startsWith("dm-")`). Открытие/закрытие —
  клик по кнопке (`stopPropagation`) + клик где угодно ещё в документе
  закрывает; клик внутри дропдауна тоже не всплывает (иначе глобальный
  обработчик закрывал бы его раньше, чем сработает пункт).
  - **Оба типа**: Включить/Выключить уведомления (`room.muted` в
    `roomsLocal`, проверяется в WS-хендлере перед `tryShowNotification`),
    Экспорт истории чата (скачивает `.txt` из уже закэшированной локально
    истории — `downloadTextFile()`, реальный `Blob`+`<a download>`, не
    требует сервера), Очистить историю (чистит ТОЛЬКО локальный кэш этого
    устройства — `saveMessages(id, [])`, серверная история комнаты не
    трогается, т.к. общего "удалить у всех" смысла в личной команде нет),
    Удалить чат/Удалить и покинуть (было и раньше — вынесено в
    `deleteCurrentRoom()`).
  - **Только для DM**: Показать профиль (`getDmPeerId()` вычисляет id
    собеседника из самого roomId `dm-<a>-<b>` — id не содержат дефисов,
    поэтому парсинг простой `slice(3).split("-")`), Установить/Изменить
    обои (`room.wallpaperUrl`, кладётся фоном на `#log` через
    `applyWallpaper()`, обычная ссылка на картинку, без загрузки файла),
    Запретить/Разрешить копирование (`room.copyDisabled` →
    `applyCopyProtection()`: класс `.no-copy` = `user-select:none` +
    `#log.oncopy = e=>e.preventDefault()`; это чисто клиентская
    "вежливая" мера, а не защита от копирования — любой человек с devtools
    её обойдёт, как и в самом телеграме).
  - **Группы/комнаты (не DM) — все пункты в итоге реализованы по
    просьбе пользователя** (изначально были осознанно пропущены как
    "нет подходящей сущности", затем добавлены полноценно):
    - **Информация о группе** (`showGroupInfo()`) — название/создатель/
      дата создания с сервера (если карточка зарегистрирована, см. ниже),
      либо честная заглушка "Общая комната (без владельца)" для комнат
      без карточки (`public`), плюс всегда — число сообщений в локальном
      кэше на этом устройстве. Никаких выдуманных цифр.
    - **Управление группой** (`showGroupManage()`/`saveGroupManage()`) —
      переименование + ссылка на аватар, реально применяется у ВСЕХ, кто
      подключён к комнате (WS `roomUpdate`), не только у автора действия.
      Требует таблицу `chat_rooms` (id, name, avatarUrl, ownerId,
      createdAt) в db.js — "карточка" поверх комнаты, которая физически
      остаётся просто строкой для WS. Комната регистрируется на сервере
      автоматически при создании через "+ Комната" (`POST
      /api/chat-rooms`, best-effort — если не получилось, комната всё
      равно работает как обычный WS-канал, просто без этих двух пунктов
      меню). `PATCH /api/chat-rooms/:id` — только владелец или админ.
    - **Создать опрос** (`showPollForm()`/`createPollFromForm()`) —
      настоящий опрос: вопрос + 2-10 вариантов, голос рассылается всем в
      комнате в реальном времени (WS `type:"poll"` на создание,
      `type:"vote"` на голос, `type:"pollUpdate"` — рассылка результата).
      Хранится в `messages.pollData` (TEXT/JSON) — опрос это ОБЫЧНОЕ
      сообщение с пустым `text` и заполненным `pollData`, а не отдельная
      сущность. Голосование одиночное (голос переносится в новый вариант
      при повторном клике). `toMessagePayload()` теперь также отдаёт `id`
      сообщения (раньше не отдавал вообще — клиенту нечем было бы
      ссылаться на конкретное сообщение для голосования).
    - **Создать список** — сообщение-чеклист (список задач с чекбоксами)
      ВНУТРИ чата, не папка для организации диалогов (это уточнил
      пользователь отдельно — первая реализация была про группировку
      диалогов в сайдбаре и была заменена на эту). Модель — та же, что у
      опросов: `messages.checklistData` (TEXT/JSON), WS `type:"checklist"`
      на создание, `type:"checklistToggle"` на клик по галочке,
      `type:"checklistUpdate"` — рассылка всем в комнате. Ключевое отличие
      от опроса: каждый пункт — НЕЗАВИСИМАЯ галочка, которую может
      поставить/снять ЛЮБОЙ участник (общее состояние, не "мой голос") —
      клик всегда переключает `item.checked`, `item.checkedBy` = кто
      отметил последним (или `null`, если сняли). `checkedBy` — это
      display name (`displayNameOf()`), НЕ login — легко напутать по
      аналогии с `poll.options[].votes`, которые хранят логины (там ок,
      потому что наружу показывается только количество, а не сами логины).
      `renderChecklistBlock()`/`toggleChecklistItem()`/`updateChecklistUI()`
      в app.js — зеркалят `renderPollBlock()`/`voteOnPoll()`/`updatePollUI()`.
    - **Трекер времени на пункте списка** ("сколько у кого времени ушло") —
      `item.timers` внутри того же `checklistData`: массив `{ login,
      displayName, totalSeconds, runningSince }`, по одной записи на
      каждого, кто хоть раз нажал "Трекер" на этом пункте. WS
      `type:"checklistTimerToggle"` — старт/стоп персонально для того, кто
      нажал (у каждого свой независимый таймер на одном и том же пункте,
      не общий на всех). Стоп считает `totalSeconds += (Date.now() -
      runningSince) / 1000` и обнуляет `runningSince`; старт просто
      выставляет `runningSince = Date.now()`. `runningSince` —
      АБСОЛЮТНЫЙ серверный timestamp, поэтому "сколько идёт прямо сейчас"
      каждый клиент честно досчитывает сам (`Date.now() - runningSince`)
      без рассинхрона часов между устройствами.
      Живой тикающий счётчик — ОДИН общий `setInterval` на всю страницу
      (`startChecklistTicker()`, стартует один раз в `initChatPage()`), а
      не по интервалу на каждый список/пункт — каждую секунду ищет все
      видимые `.checklist-timer-breakdown[data-has-running="true"]` и
      перерисовывает их из локального кэша сообщений (`loadMessages`),
      который уже обновляется на каждый `checklistUpdate` по WS. Если
      открыто несколько списков с активными таймерами одновременно — все
      тикают от одного и того же интервала, лишних таймеров не плодится.
    - **Пожаловаться** (`sendReportFromForm()`) — новая таблица
      `chat_reports` (id, room, reporterId, note, createdAt), `POST
      /api/chat-reports`. Админка: секция "Жалобы на переписку" в
      admin.html (`renderAdminChatReports()`) — `GET/DELETE
      /api/admin/chat-reports`, кнопка "Отметить рассмотренной" просто
      удаляет запись (без статусов "открыта/закрыта" — MVP).

**Анимация сворачивания — доработана (изначальная версия дёргалась).**
Проблема была в двух местах: (1) подписи пунктов прятались через
`display:none` — исчезали/появлялись МГНОВЕННО, пока сама колонка
`.sidebar` ещё плавно анимировала `width`, из-за чего разворот выглядел
рывком, а не одной анимацией; (2) центрирование иконки в свёрнутом виде
делалось через `justify-content:center` — это скачкообразное свойство
(браузер физически не умеет его анимировать/интерполировать), иконка
мгновенно "прыгала" в центр строки. Исправлено:
- Разметка в `renderMenu()` (components.js) теперь оборачивает иконку и
  подпись в отдельные `<span class="nav-icon">`/`<span class="nav-label">`
  (было — голый `<span>` только вокруг подписи). `.nav-icon` —
  fixed-width (18px) обёртка, поэтому иконка НИКОГДА не двигается сама
  по себе при сворачивании/разворачивании.
- `.nav-label`/`.logo-text` вместо `display:none` теперь анимируются
  через `max-width` + `opacity` (transition на оба свойства) — подпись
  плавно сжимается и растворяется синхронно с шириной сайдбара, а не
  исчезает скачком.
- Центрирование иконки в свёрнутом виде — теперь через симметричный
  `padding-left/right:17px` на строке пункта (вместо `justify-content`),
  который, в отличие от `justify-content`, браузер честно анимирует
  вместе с шириной колонки.
- `.sidebar` transition — `width` + `padding` на `cubic-bezier(.4,0,.2,1)`
  0.25s (было просто `width .2s ease`) — чуть плавнее и покрывает оба
  меняющихся свойства.
- Заодно: `.logo-circle` (лого "LÖ", по которому кликают, чтобы
  свернуть/развернуть) получил `cursor:pointer` в БАЗОВОМ правиле — до
  этого курсор был `pointer` только в свёрнутом состоянии, хотя кликать
  можно в обоих.

**[БАГ-ФИКС] История чата с сервера никогда не отображалась.**
`wss.on("connection", ...)` в server.js всегда честно шлёт
`{type:"history", data:[...]}` (последние 50 сообщений комнаты) сразу
после подключения — но клиентский WS-обработчик в app.js
(`connectWebSocket()`) проверял только `"presence"`/`"roomUpdate"`/
`"pollUpdate"`/`"checklistUpdate"`/`"system"`/`"chat"` — тип `"history"`
никогда не обрабатывался и молча игнорировался. На практике это
означало: реальная история чата существовала в БД, но новый человек
(или чужой браузер/устройство без локального кэша — вся история чата
на клиенте держится в `localStorage`, см. `loadMessages`/`saveMessages`)
не видел вообще НИЧЕГО из прошлой переписки, пока не получал сообщения
"живьём" по WS уже будучи подключённым. Баг всплыл при создании тестового
аккаунта "Иван Петров" и переписке с админом — админ открыл диалог и
увидел пустой чат, хотя сообщение точно было отправлено и сохранено.
Исправлено — добавлен обработчик `msg.type === "history"`: мержит
`msg.data` с уже сохранённым локальным кэшем комнаты по `id` сообщения
(не затирает кэш целиком), при необходимости заводит локальную карточку
комнаты в `roomsLocal` (если открыли диалог впервые на этом устройстве,
например по ID, и сами ещё ничего не писали), перерисовывает список
диалогов и текущий лог. Затрагивает вообще ВСЕ комнаты/диалоги, не
только новые — то есть любой открытый впервые на новом устройстве чат
теперь наконец подтягивает реальную историю с сервера, а не только то,
что было получено "живьём".

**Переработан рендер сообщений чата — аватар/имя по контексту,
раскладка по ширине окна.** Раньше КАЖДОЕ сообщение (и своё, и чужое)
показывало подпись "Имя, время" и декоративный кружок-аватар (через
CSS `::before`, `--avatar-url` custom property), а сами сообщения
всегда шли одной колонкой на всю ширину `#log`. По референсам
(скриншоты Telegram) переделано на структуру `.msg-row` →
`.msg-avatar` (опционально) + `.msg-bubble` (`appendMessageToLog()` в
app.js, `data-message-id` теперь на `.msg-bubble`, а не на строке —
`updatePollUI()`/`updateChecklistUI()` ищут по этому атрибуту и
дописывают опрос/чек-лист туда же, они не менялись).

Кто получает аватар/имя — зависит ТОЛЬКО от того, чьё сообщение и
личный это диалог или комната, но НЕ от ширины экрана:
- своё сообщение (`isMe`) — никогда ни аватара, ни имени (понятно и
  так, по цвету/выравниванию);
- чужое в личном диалоге (`currentRoom.startsWith("dm-")`) — аватар
  есть, имени нет (собеседник один, он и так виден в шапке чата);
- чужое в комнате/группе — аватар И имя (отправителей несколько,
  нужно различать, кто есть кто).
Аватар при этом рендерится, только если у конкретного сообщения есть
снимок `avatar` (см. выше про снимок на момент отправки) — старые
сообщения без него по-прежнему честно показывают имя без кружка,
никаких выдуманных аватарок.

Время сообщения (`.msg-time`) — отдельный элемент, ВСЕГДА внизу пузыря
прижат вправо (`text-align:right`), а не сверху рядом с именем, как
было раньше (единый `.meta` с текстом `"Имя, время"`). Имя (если
показывается по правилам выше) осталось отдельной строкой сверху
пузыря (`.meta`, теперь содержит только имя, без времени). Работает
одинаково при любой ширине экрана — вниз-вправо время уходит и в
колонке (≥1200px), и в пузыре (<1200px).

Раскладка ("друг под другом одной колонкой" vs "пузыри друг напротив
друга, свои справа") зависит ТОЛЬКО от ширины окна — новый брейкпоинт
**1200px**, специально заведённый ОТДЕЛЬНО от основного мобильного
768px (тот двигает сайдбар/переключение списка↔чата на телефоне, к
рендеру самих сообщений отношения не имеет):
- `≥1200px` — `.msg-bubble` растягивается на всю ширину строки
  (`flex:1 1 auto`), сообщения идут одной колонкой, как раньше;
- `<1200px` (`@media (max-width: 1199.98px)` в styles.css) —
  `.msg-bubble` получает `max-width:78%`, `.msg-row.me` —
  `justify-content:flex-end` (свои вправо), у чужих остаётся
  `flex-start` (по умолчанию) — итого пузыри как в обычном мессенджере.
  Это НЕ переопределяет то, что видно, только то, КАК это расположено —
  на <1200px в комнате по-прежнему видно и аватар, и имя, просто в
  виде пузыря, а не строки на всю ширину.

**Открытый чат на мобильном — теперь настоящий полноэкранный "локальный"
режим, растянутый на всю высоту.** Раньше `.chat-main` на мобильном был
`height:auto` внутри обычного скроллящегося потока страницы (нужного
другим мобильным страницам — там `body{height:auto;overflow:auto}`),
а `#log` был жёстко ограничен `max-height:55vh` — из-за этого под чатом
оставался пустой "хвост" страницы, а сам чат не занимал реально видимую
высоту экрана. Теперь `.chat-layout.chat-open` (мобильный `@media`) —
`position:fixed; inset:0;` поверх ВСЕЙ страницы, включая обычную шапку
(хамбургер/заголовок/тема) — она специально перекрывается, а не просто
остаётся сверху: у чата уже есть свой хедер с кнопкой "назад", второй
хедер был бы лишним (как в телеграме/whatsapp). `#log` больше не имеет
`max-height:55vh` — вернулся к обычному `flex:1 1 auto` (из базового,
некопированного мобильного правила), поэтому честно тянется на всю
доступную высоту между хедером чата и полем ввода.

Высота берётся из CSS-переменной `--app-vh` (не `100vh`/`100dvh`
напрямую) — `initMobileChatViewport()` в app.js подписывается на
`window.visualViewport.resize` и пишет туда `visualViewport.height`.
Это принципиально: на iOS Safari открытие экранной клавиатуры НЕ
меняет layout viewport (от которого считаются `vh`/`dvh`) — чат на
`100dvh` просто оказался бы наполовину под клавиатурой. `visualViewport`
— единственный API, честно отражающий видимую (не перекрытую
клавиатурой) область на всех современных мобильных браузерах, и его
`resize` событие срабатывает и при открытии/закрытии клавиатуры, и при
повороте экрана. Функция вызывается безусловно в `DOMContentLoaded`
(как `initMobileMenu()`) — на десктопе `--app-vh` тоже выставляется, но
ни на что не влияет, т.к. используется только внутри
`.chat-layout.chat-open` в мобильном `@media`-блоке.

## Звонки (аудио через WebRTC)

Первая версия — только аудио, только 1-на-1 (личный диалог); видео и
групповые звонки — осознанно не в этом заходе (см. ниже).

- **Сигналинг** — `server.js`, новые типы WS-сообщений `call-offer`/
  `call-answer`/`call-ice`/`call-reject`/`call-end`/`call-busy` в
  общем `ws.on("message", ...)` (там же, где `chat`/`poll`/`checklist`).
  Сервер НЕ участвует в самом голосе — только пересылает служебные
  SDP/ICE-сообщения от одного пользователя к другому, находя получателя
  по `login` (а НЕ по `room` — звонок не привязан к тому, какая комната
  у кого открыта в WS, это независимая вещь). `from`/`fromDisplayName`/
  `fromAvatar` сервер всегда подставляет сам из `client.login` (текущего
  WS-соединения), не доверяя телу сообщения — звонящий не может выдать
  себя за другого. Если получатель ни к чему не подключён — звонящему
  честно летит `call-unavailable` вместо вечных гудков в пустоту.
- **Клиент** — `app.js`, секция "ЗВОНКИ (аудио через WebRTC)" перед
  `connectWebSocket()`. `activeCall` — единственный глобальный объект
  состояния звонка (`callId`, `peerLogin`, `pc` — RTCPeerConnection,
  `localStream`, `status`: `outgoing`/`incoming`/`connected`/`ended`).
  UI — `renderCallOverlay()`, оверлей создаётся прямо в JS (как
  `openPhotoLightbox()`), а НЕ часть разметки chats.html — поэтому
  входящий звонок виден на ЛЮБОЙ странице (WS глобальный, см.
  `connectWebSocket()`), не только в чатах. `handleCallSignal()` —
  диспетчер входящих `call-*` сообщений, подключён в общем WS-обработчике
  через `CALL_MESSAGE_TYPES`.
  ICE-кандидаты, пришедшие раньше `setRemoteDescription` (обычная гонка
  в WebRTC) — складываются в `activeCall.pendingCandidates` и
  применяются после того, как remote description выставлен (логика
  общая что для звонящего, что для принимающего).
- **Кнопка звонка** — `#chatCallBtn` в шапке чата (`chats.html`), рядом
  с кнопкой-троеточием; видимость переключает `updateChatHeader()` —
  только для `dm-*`-комнат (`hidden` для комнат/групп, групповых звонков
  нет). Значок и обработчик клика вешаются один раз в `initChatPage()`
  (обычный паттерн этого файла — один слушатель на всю жизнь страницы,
  не перевешивается на каждую смену чата).
- **STUN, без TURN** — `CALL_ICE_SERVERS` в app.js, только публичный
  Google STUN. Работает в подавляющем большинстве сетей (обычный
  домашний/мобильный NAT), но за особо строгим NAT (часть корпоративных
  сетей, symmetric NAT) соединение может не установиться — для железной
  гарантии везде нужен свой или платный TURN-сервер, это отдельная
  инфраструктурная штука (не просто конфиг), сознательно не в этом
  заходе.
- **Ограничение архитектуры (осознанное, важное).** Проект
  многостраничный (обычные переходы между `.html`, НЕ SPA) — значит
  `RTCPeerConnection` физически не переживает переход на другую страницу
  (вся JS-память уничтожается браузером при навигации, как при обычной
  перезагрузке). `beforeunload` в app.js best-effort шлёт `call-end`
  собеседнику при уходе со страницы посреди разговора (чтобы у него не
  остался зависший "идёт разговор"), но сам звонок в любом случае
  обрывается — рассчитано, что говорить будут, оставаясь на одной
  странице (chats.html), как и будет в подавляющем большинстве случаев.
- **Иконки** — добавлены `call` (трубка), `mic`/`micOff` в
  `ICON_PATHS` (components.js). Кнопки "отклонить"/"сбросить" — та же
  иконка `call`, развёрнутая на 135° через CSS (`.call-btn-end svg`) —
  стандартный визуальный приём "положить трубку", отдельная иконка не
  понадобилась.
- **Проверено:** UI всех состояний (исходящий/входящий/отклонён),
  реальный round-trip через сервер (`call-offer` → относится по login,
  `from*` честно подставлены сервером), путь "собеседник не в сети"
  (`call-unavailable`), корректная очистка состояния после звонка.
  Реального сквозного аудио между двумя живыми людьми проверить не
  удалось — у автоматизированного браузера в этом окружении нет
  доступа к микрофону (`getUserMedia` заблокирован), и это ожидаемо
  ловится кодом (`"Нет доступа к микрофону"`), не роняя ничего. Логика
  `RTCPeerConnection`/`getUserMedia` — стандартные, широко
  использующиеся браузерные API; корректность самого голоса стоит
  проверить на двух настоящих устройствах с микрофоном при первой
  возможности.

**Следующий шаг (не сделан):** видеозвонки — тот же сигналинг уже
поддерживает флаг `video` в `call-offer`, останется добавить
`getUserMedia({video:true})`, `<video>`-элементы для локального/
удалённого потока и переключение "аудио/видео" в UI кнопки звонка.

## PWA — устанавливается на телефон ("Добавить на главный экран")

Первый шаг к мобильному приложению — не нативный APK, а PWA
(Progressive Web App): телефон предлагает установить сайт как обычное
приложение (иконка на главном экране, отдельное окно без адресной
строки браузера, `theme_color` красит системную шторку). Настоящий
`.apk`-файл — следующий, отдельный шаг поверх этого (см. ниже).

- **`manifest.json`** (корень проекта) — имя, иконки, `display:
  standalone`, `theme_color: #16a34a` (тот же зелёный, что у бренда),
  `start_url: /index.html`. Подключён `<link rel="manifest"
  href="manifest.json">` во ВСЕХ 14 HTML-страницах (плюс `<meta
  name="theme-color">` и `<link rel="apple-touch-icon">` — iOS манифест
  умеет далеко не всё, apple-touch-icon нужен отдельно).
- **`icon-192.png`/`icon-512.png`** — сгенерированы программно (canvas
  в браузере: тот же радиальный градиент и стиль "LÖ", что у
  `.logo-circle` в styles.css, см. историю сессии — временная HTML-
  страница с `<canvas>` рисовала иконку, дальше PNG сохранён на диск
  через ВРЕМЕННЫЙ dev-роут в server.js, роут и страница удалены сразу
  после использования, ничего постоянного не осталось).
- **`sw.js`** (service worker, корень проекта) — минимальный, нужен
  прежде всего для критерия "устанавливаемости" (Chrome требует хотя бы
  один `fetch`-обработчик у SW). Кэширует только статическую ОБОЛОЧКУ
  (`styles.css`/`app.js`/`components.js`/иконки) по стратегии
  "сеть в приоритете, кэш — запасной вариант при обрыве связи". `/api/*`
  и не-GET запросы НЕ кэшируются никогда — посты/сообщения/друзья
  обязаны быть свежими, а не залежавшимся снимком. Регистрируется в
  app.js (`navigator.serviceWorker.register("/sw.js")`, после
  `window.load`) — один блок кода в самом начале файла, работает на
  всех страницах.
- Все 4 новых файла (`manifest.json`, `sw.js`, `icon-192.png`,
  `icon-512.png`) добавлены в `PUBLIC_FILES` в server.js — тот же
  allowlist-механизм, что у остальной статики (иначе 404-ились бы).

**Что дальше, если понадобится настоящий `.apk` (отдельный шаг, не
сделан):** сайт нужно сначала задеплоить на реальный публичный
HTTPS-домен (localhost не подходит — по правилам проекта деплой только
с явного разрешения, см. "Что НЕ делать без явного разрешения" ниже),
после чего бесплатный сервис PWABuilder.com (или CLI Bubblewrap)
оборачивает уже готовую PWA в подписанный `.apk`/`.aab` без переписывания
кода — ту же PWA-разметку, что уже есть.

## Логотип — остаётся исходный ("LÖ" текстом)

В сессии перебирались варианты фирменного значка вместо простого текста
"LÖ" в `.logo-circle` (улитка вместо "ö", лягушка вместо "Ö", камыш+
лягушка как "L"+"Ö") — все показывались только как превью
(Artifact), в проект не попадали или были откачены обратно по просьбе
пользователя. Итог: логотип остался как был изначально — `.logo-circle`
в `renderMenu()` (components.js) и в `auth.html` содержит просто текст
`LÖ` на радиальном зелёном градиенте (белый→`#86efac`→`#16a34a`),
`icon-192.png`/`icon-512.png` — тот же текст на белом скруглённом
квадрате. Полноразмерной надписи-логотипа ("Lömo" леттерингом) на
`auth.html` тоже нет — там только карточки входа/регистрации, как и до
экспериментов с лого.

**Правило на будущее (см. память агента):** любые правки логотипа —
сначала показать превью (например, через Artifact), дождаться явного
"да" от пользователя, и только потом вносить в файлы проекта
(components.js, styles.css, auth.html, icon-*.png). Не применять с
первого захода, как это по ошибке произошло один раз в начале.
