# LÖMO — контекст для агента

## О проекте
Соц-сеть с чатом: Express + SQLite (встроенный `node:sqlite`, без внешних
npm-зависимостей для БД) + WebSocket на backend, мультистраничный vanilla
JS/HTML/CSS на frontend (без сборщика, без TS, без тестов).
Требуется Node.js >= 22.5 (модуль `node:sqlite`); разрабатывалось и
протестировано на Node 24 LTS.

## Стек и структура
- `server.js` — весь backend в одном файле: Express REST + `WebSocketServer`
  (чат, история сообщений хранится в SQLite, лимит 50 последних на комнату).
  Все `/api/*`-маршруты, кроме `/api/register` и `/api/login`, защищены
  `requireAuth` (JWT в заголовке `Authorization: Bearer`).
  Загруженные файлы раздаются отдельным статическим маршрутом `/uploads`
  (папка `process.env.UPLOADS_DIR`, по умолчанию `./uploads`) — НЕ через
  `PUBLIC_FILES`-allowlist, который отдаёт только конкретный список HTML/CSS/
  JS-файлов (важно: если добавляешь новую HTML-страницу — её имя нужно
  вписать в `PUBLIC_FILES`, иначе она будет 404-иться). Этот `/uploads`-роут
  зарегистрирован РАНЬШЕ корневого `express.static(cwd)` — так и должно
  быть, иначе корневая статика сама находит файлы в `uploads/` (это реальная
  подпапка проекта) и отдаёт их в обход заголовков безопасности ниже.
  `POST /api/upload` — общий загрузчик (фото к посту, файл в чат): картинки
  отдаются инлайн, всё остальное — с `Content-Disposition: attachment`
  (чтобы .html/.svg с чужим скриптом не выполнился в контексте нашего
  origin), плюс блок-лист опасных расширений на входе (`DANGEROUS_EXT`).
  Имя файла из `req.file.originalname` ВСЕГДА пропускай через
  `fixFilenameEncoding()` перед сохранением/ответом — busboy по умолчанию
  декодирует не-ASCII имена (кириллицу и т.д.) как latin1, без этого
  получаются кракозябры.
- **`login` vs `displayName`**: `login` — фиксированный технический
  идентификатор (уникальность, вход, WS-подключение, `dm-`-комнаты кодируются
  по ID, не по login) и НИГДЕ не редактируется через UI. `displayName` —
  то, что реально видят другие пользователи (посты, комментарии, друзья,
  чат) и что можно поменять на "Мой аккаунт". Раньше на аккаунте было поле
  "Как тебя зовут?", которое меняло имя ТОЛЬКО в localStorage самого
  пользователя — нигде больше не отражалось, отсюда путаница. Теперь это
  настоящее поле `users.displayName`, обновляется через `PATCH /api/me`,
  и `displayNameOf(user)` в `server.js` — общая точка, откуда оно
  подставляется в `authorName` постов/комментариев и `toPublicUser`.
  `login` также больше НЕ показывается в UI (`account.html`/`profile.html`) —
  публично виден только `displayName` и ID; сам логин по-прежнему приходит
  в ответах `/api/me` и `/api/user-by-id/:id` (нужен клиенту для WS и
  внутренней логики), просто не рендерится на экран.
- **ID пользователя** — с этого захода короткий: 6 цифр + 2 заглавные буквы
  (например `771833RN`), генерируется `generateUserId()` в `server.js`
  (проверяет уникальность через `stmts.findUserById`, до 50 попыток).
  Раньше был `crypto.randomUUID()`. Существующие на момент смены формата
  аккаунты (admin/visual_test/visual_test2) были миграцией переведены на
  новый формат одноразовым скриптом — ID пересчитан и везде корректно
  перепривязан (`posts.ownerId/authorId`, `likes.userId`,
  `comments.authorId`, `friendships.userA/userB/requestedBy` — с
  восстановлением порядка `userA < userB`, `groups.ownerId`,
  `group_members.userId`, `albums.ownerId`, `photos.ownerId`,
  `stories.ownerId`); все, кто был залогинен на момент миграции, были
  разлогинены (старый ID в JWT переставал существовать в БД). Скрипт был
  одноразовым и удалён — если понадобится мигрировать ID снова (например,
  после ручной правки БД), писать по тому же принципу: пройтись по всем
  таблицам с `ownerId`/`authorId`/`userId`, заменить в транзакции, `users.id`
  обновлять последним.
- `db.js` — подключение к SQLite (файл по пути `process.env.DB_PATH`,
  по умолчанию `./data/lomo.db`). Таблицы: `users` (+`about`, +`displayName`
  — оба раньше жили только в localStorage и не были видны другим, теперь
  настоящие поля, обновляются через `PATCH /api/me`), `messages`
  (+`fileUrl`/`fileName` — вложение к сообщению чата; `avatar` и
  `fromDisplayName` — снимок аватара/имени отправителя НА МОМЕНТ отправки,
  не обновляются задним числом у старых сообщений при смене профиля), `posts` (стена —
  `ownerType` `'user'`|`'group'` + `ownerId`, общая для профилей и групп;
  +`photoUrl` — фото к посту, рендерится ДО текста), `likes`, `comments`
  (+`photoUrl` — фото к комментарию, рендерится ПОСЛЕ текста, то есть в
  обратном посту порядке — так и задумано), `friendships` (пара id хранится
  как `userA < userB`, см. `friendPair()` в `server.js`), `groups`,
  `group_members`, `albums`, `photos`, `stories` (сторис на Главной, живут
  24 часа — см. `STORY_TTL_MS`, чистятся лениво при каждом `GET /api/stories`,
  без крона). Новые колонки в уже существующие таблицы добавляются безопасно
  через `ensureColumn()` (аддитивный `ALTER TABLE ADD COLUMN`, ничего не
  удаляет) — паттерн для будущих миграций. `node:sqlite` принимает только
  позиционные `?`-параметры — НЕ `@name`/`:name` (лишний ключ в объекте
  кидает `Unknown named parameter`).
- `app.js` — вся клиентская логика и роутинг по имени текущего HTML-файла
  (index.html, account.html, auth.html, chats.html, users.html, admin.html,
  groups.html, group.html, profile.html, friends.html, photos.html,
  music.html, video.html, books.html). Общий рендер стены — функция
  `initWall()`, переиспользуется на account.html/profile.html/group.html.
  `index.html` (Главная) — НЕ профиль, это лента: сторис-ряд
  (`initStoriesRow()`) + агрегированная лента публикаций (`renderFeed()` →
  `GET /api/feed` — свои посты + посты друзей + посты групп, где состоишь).
  Личный профиль/редактирование/своя стена — на `account.html`
  (`initAccountPage()`, бывшая `initHomePage()`).
- Стили — `styles.css`, без препроцессоров. Визуально всё ещё в текущем
  «стеклянном» стиле — полноценный ретро-скин под ВК 2010 (шрифты, цвета
  страницы целиком) по-прежнему не делали; сделали только структурную часть
  «как в ВК 2010» — сторис + лента вместо профиля на Главной.
- **Иконки** — везде инлайн-SVG вместо эмодзи. Набор путей и хелпер
  `icon(name, size)` объявлены в `components.js` (`ICON_PATHS`) и доступны
  из `app.js` без импорта — оба подключены обычными `<script>` без
  `type="module"`, поэтому top-level `const`/`function` из components.js
  видны в app.js (один script scope документа; `components.js` должен
  грузиться ПЕРВЫМ). Используется и в меню (`renderMenu()`/`renderHeader()`
  в components.js), и в действиях (лайк/комментарий/прикрепить/удалить/
  отправить и т.д. в app.js). Добавляя новую иконку — впиши путь в
  `ICON_PATHS`, только `stroke`, без лишних `fill` (кроме треугольника play
  в `video` — там осознанно `fill="currentColor" stroke="none"` на самом
  `<path>`, это единственное исключение).
- **Мобильная адаптация** — сайдбар на экранах `≤768px`
  (`@media (max-width:768px)` в конце `styles.css`) превращается в
  выезжающую слева панель (`position:fixed`, `transform:translateX(-100%)`
  → `.sidebar.open{transform:translateX(0)}`) поверх контента, с
  затемняющей подложкой `.sidebar-backdrop` и кнопкой-бутербродом
  `#menuToggleBtn` в шапке (видна только на мобильном). Вся логика
  открытия/закрытия — `initMobileMenu()` в app.js, вызывается БЕЗУСЛОВНО
  первой строкой в `DOMContentLoaded` (до проверки залогинен ли юзер),
  потому что должна работать и на `auth.html` тоже. `auth.html` не грузит
  `components.js` (у него нет полноценного меню) — бутерброд/крестик/луна
  там захардкожены статикой прямо в HTML теми же SVG-путями, что и в
  `ICON_PATHS`; если поменяешь путь иконки в `ICON_PATHS` — обнови и
  `auth.html` вручную, они не связаны программно.

## Известные проблемы, приоритет исправления

1. **[РЕШЕНО, но нужно ручное действие] Раньше в `server.js` был захардкожен
   реальный логин/пароль от MongoDB Atlas как fallback-значение `MONGO_URI`.**
   Теперь БД — локальный файл SQLite (`db.js`, путь через `.env` → `DB_PATH`),
   MongoDB и Atlas в проекте больше не используются.
   - **старый пароль пользователя БД в MongoDB Atlas всё ещё стоит сменить/
     удалить вручную — он раньше был закоммичен в открытом виде, агент не
     может сделать это сам, обязательно напомни об этом человеку**
   - на VPS файл `data/lomo.db` — это единственный источник данных, у него
     нет автоматических бэкапов, как у managed-БД; нужно резервное копирование
     этого файла вручную/по крону

2. **[РЕШЕНО]** Пароли хешируются через встроенный `crypto.scrypt`
   (`hashPassword`/`verifyPassword` в `server.js`, формат колонки —
   `"соль:хеш"`, обе части hex). Не bcrypt/argon2 намеренно — это нативные
   npm-модули, а на этой машине уже был случай, когда нативный модуль
   (`better-sqlite3`) не собрался без Visual Studio Build Tools; scrypt
   встроен в Node и даёт тот же уровень стойкости. При старте сервера
   одноразово мигрирует старые открытые пароли в хеш (`migratePlaintextPasswords`
   в `server.js`, определяет по regex — если значение не похоже на
   `"соль:хеш"`, значит ещё не хешировано).

3. **[РЕШЕНО]** REST и WebSocket защищены JWT. REST-маршруты (кроме
   register/login) проверяют `Authorization: Bearer` через `requireAuth`.
   WS-подключение (`connectWebSocket()` в `app.js`) раньше передавало
   `login` как обычный query-параметр без токена — сервер верил ему на
   слово, и теоретически можно было подключиться и слать сообщения от
   чужого имени, просто зная чей-то (публичный, виден в поиске) login.
   Теперь клиент шлёт `?token=<JWT>` вместо `?login=`, а `wss.on(
   "connection")` в server.js верифицирует токен через `jwt.verify()` и
   достаёт `login` ИЗ ПОДПИСАННОГО payload — сырой login от клиента
   больше нигде не участвует. Нет валидного токена → `ws.close(4001,
   "unauthorized")` сразу, до добавления в `clients`. Login, которого нет
   в БД (аккаунт удалён после выдачи токена) → `ws.close(4004, "user not
   found")`. Забаненный — как и раньше, `ws.close(4003, "banned")`, но
   теперь после того, как личность уже надёжно подтверждена токеном, а
   не query-параметром. Проверено вручную: подключение без токена и с
   заведомо невалидным токеном оба получают `4001`; обычный чат
   (история, отправка сообщений) продолжает работать как раньше.

4. **[РЕШЕНО]** `GET /api/user-by-id/:id` реализован в `server.js` —
   поиск диалога по ID в чате и просмотр чужого профиля (`profile.html`)
   работают.

5. **[РЕШЕНО]** Старый `admin.js` (мёртвый localStorage-конфиг
   `mychat_admin_v1`, нигде не читался) удалён вместе со ссылкой на него из
   `PUBLIC_FILES`. `admin.html`/`users.html` теперь настоящая админка — см.
   раздел «Админка» ниже.

6. **[ЧАСТИЧНО РЕШЕНО, осознанный компромисс] `admin.html`/`users.html` сами
   HTML-страницы по-прежнему отдаются любому по прямой ссылке** (они в
   `PUBLIC_FILES`, как и остальные страницы), но это уже не проблема
   безопасности: весь функционал внутри них работает через `/api/admin/*`,
   а туда пускает только `requireAuth` + `requireAdmin` (проверяет
   `req.user.isAdmin` из БД на каждый запрос). Не-админ откроет пустые
   страницы — данные всё равно не подтянутся. Пункт навигации на «Админ»/
   «Пользователи» тоже скрыт на клиенте для не-админов, как и раньше.

## Соц-фичи (стена, друзья, группы, фото) — сознательные упрощения

Реализовано: стена профиля/группы (посты, лайки, комментарии, опционально
фото к посту), друзья (заявки/подтверждение, одна строка поиска — логин ИЛИ
точный ID через `GET /api/users?q=`, см. `searchUsers` в `server.js`),
реальные группы (создание, вступление, выход, владелец не может выйти без
удаления группы), фотоальбомы с загрузкой файлов через `multer` (только
`image/*`, лимит 8MB — отдельно от общего `/api/upload`), чат с вложением
файла (любой не-опасный тип, лимит 20MB, картинки рендерятся инлайн,
остальное — ссылкой на скачивание).

Сознательно НЕ сделано в этом заходе (не баги, а осознанные границы MVP):
- Стены **публичные** — читать может любой залогиненный пользователь, без
  проверки дружбы.
- Постить можно только **на свою стену** (или на стену группы, если ты
  участник) — писать на чужой профиль нельзя.
- Нет уведомлений (о заявке в друзья, лайке, комментарии) — только то, что
  видно при заходе на страницу.
- Нет пагинации нигде (посты, комментарии, друзья, группы, фото) — ок при
  игрушечном объёме данных, но всё грузится целиком.
- При удалении группы (`DELETE /api/groups/:id`) посты этой группы удаляются,
  но их лайки/комментарии — нет (остаются висеть в БД как мусор, на
  функциональность не влияет).
- У групп аватар — только URL-строка (как у пользователя), а не файл, в
  отличие от фотоальбомов.

## Админка (`admin.html`, `users.html`)

Реализована по мотивам обычных соц-сетей: обзор-статистика, модерация
публикаций/групп, управление пользователями. Всё под `requireAuth,
requireAdmin` в `server.js`.

- `users.users.isBanned` (0/1) и `users.createdAt` — новые колонки через
  `ensureColumn()`.
- **`requireAuth` теперь бьёт в БД на КАЖДЫЙ запрос** (`stmts.findUserById`),
  а не доверяет только полю из JWT — из-за этого бан/разбан и выдача/снятие
  прав админа применяются мгновенно, без ожидания истечения токена (7 дней).
  То же самое на подключении к WS: `connectingUser.isBanned` проверяется до
  `ws.close(4003, "banned")`. `POST /api/login` тоже проверяет `isBanned` и
  отвечает 403.
- `GET /api/admin/stats` — счётчики (пользователи/админы/забаненные/посты/
  комментарии/сообщения/группы/фото/сторис).
- `GET /api/admin/users?q=` — поиск по логину, `toAdminUser()` (расширяет
  `toPublicUser` полями `isAdmin`/`isBanned`/`createdAt`).
- `PATCH /api/admin/users/:id` — переключает `isAdmin`/`isBanned`; блокирует
  снятие прав/бан самого себя (отдельные сообщения об ошибке на каждый
  случай, кнопки в `users.html` для своей строки тоже задизейблены на клиенте
  с тултипом — двойная защита).
- `DELETE /api/admin/users/:id` — полное каскадное удаление: свои группы
  удаляются целиком (с постами/лайками/комментариями/фото), собственные
  посты/комментарии/лайки/фотоальбомы/сторис/дружбы/членства в группах —
  тоже; файлы фото удаляются с диска. Себя удалить нельзя.
- `GET /api/admin/posts?q=` — полнотекстовый поиск по всем постам (любой
  стены), с `contextLabel`. `GET /api/admin/groups` — все группы.
- `DELETE /api/comments/:id` — новый роут (автор либо админ). Удаление
  поста/фото/сторис теперь тоже пропускает владельца ИЛИ админа
  (`req.user.isAdmin` в условии).
- Фронтенд: `initAdminPage()`/`initUsersPage()` в `app.js`, роутинг по
  `path.endsWith("admin.html"/"users.html")`. Кнопка модерации на карточке
  поста переиспользует существующий `renderPostCard()` — просто добавляет
  одну кнопку в `.post-actions`.

## Автомодерация (`moderation.js`)

Локальный офлайн-фильтр (без внешних AI-сервисов и API-ключей — осознанный
выбор пользователя между "просто и бесплатно" и "платно через Claude API";
если позже понадобится реально понимать смысл текста/картинок — это будет
отдельный, более дорогой заход). НЕ анализирует смысл — сопоставляет с
паттернами. Две независимые проверки:

- **Текст** — `moderateText(text)` в `moderation.js`, вызывается в
  `POST /api/posts` и `POST /api/posts/:id/comments` перед вставкой в БД.
  Нормализует текст ПОСЛОВНО (leet-замены цифрами, латиница вместо похожей
  кириллицы, разделители типа "с.у.к.а") — специально не схлопывает весь
  текст в одну строку, чтобы не склеивать соседние слова и не плодить
  ложные срабатывания. Считает score по корням слов (не полным словам —
  ловит склонения) + эвристикам (капс, спам-ссылки, повторы символов).
  `score >= 80` → **reject** (публикация блокируется сразу, 400 с причиной,
  ничего не пишется в БД). `score 30-79` → **flag** (публикуется, но
  `moderationStatus='flagged'` — скрыта из ленты/стены/комментариев для
  всех, кроме автора и админа, см. `filterVisible()` в server.js, до
  ручного решения в админке). `< 30` → clean, как обычно.
  Корни для "разжигания" (`GROUP_ROOTS`+`THREAT_ROOTS`, совпадение обоих
  в одном тексте) — эвристика на случай, когда явного мата нет, но по
  совокупности похоже на угрозу в адрес группы людей (мотивирующий кейс:
  "Евреи пожалеют о содеянном, все они виноваты" — ловится этой эвристикой,
  НЕ словарём мата). Корни держи короткими из-за "плавающих" гласных в
  русском склонении (хохол/хохлы) — иначе легко словить ложные срабатывания
  (`хохо` как корень ловил бы и "хохотать").
- **Картинки** — `isRealImage(buffer)` в `moderation.js`, проверяет
  сигнатуру первых байт файла (JPEG/PNG/GIF/WEBP), вызывается в
  `POST /api/upload` и `POST /api/albums/:albumId/photos` ПОСЛЕ того, как
  multer уже записал файл на диск (`rejectIfFakeImage()` в server.js читает
  16 байт, удаляет файл при несовпадении). Ловит только случай "файл выдаёт
  себя за картинку, а на самом деле не картинка" (подмена mimetype) — само
  содержимое картинки (что на ней) НЕ анализируется, это по-прежнему
  недоступно офлайн без внешнего сервиса.

Схема: `posts`/`comments` получили колонки `moderationStatus` ('clean' по
умолчанию | 'flagged') и `moderationReason` (text). Админка
(`admin.html` → секция «На проверке») дёргает `GET /api/admin/moderation`
(отдаёт весь список flagged) и одобряет через `PATCH
/api/admin/posts/:id/approve` / `PATCH /api/admin/comments/:id/approve`
(сбрасывает статус в 'clean'); удаление — существующими `DELETE`-роутами.

**Важно про `[hidden]`**: на `.moderation-reason` НЕ ставь свойство
`display` в CSS — это тот же баг, что уже ловили в сессии на `#preview`:
author-стиль с `display` всегда бьёт UA-правило `[hidden]{display:none}`,
и пустой блок остаётся видимым (8px пустоты) даже с атрибутом `hidden`.
Используй `width: fit-content` вместо `display: inline-block`, если нужен
блок по ширине контента.

## Мобильная адаптация (продолжение)

`users.html` — таблица не влезала по ширине на `≤768px` (кнопки действий
обрезались до нечитаемых огрызков типа "Сд", "Заб"). Фикс — классический
"responsive table": в мобильном `@media` блоке `table/tbody/tr/td`
получают `display:block`, `thead` скрыт, `td[data-label]::before`
подставляет подпись поля через CSS `content: attr(data-label)`. `data-label`
проставляется в JS (`initUsersPage()` в app.js) только на ячейки
логина/статуса — у ячейки "Пользователь" (аватар+имя) и "Действия"
(кнопки) подписи не нужны, они самоочевидны. Если добавляешь новую колонку
в эту таблицу — не забудь `data-label`, иначе на мобильном у неё не будет
подписи поля.

**Скролл в выезжающем мобильном меню.** Раньше скроллился весь `.sidebar`
целиком — на невысоких экранах (или когда залогинен админ и в меню
добавляются "Админ"/"Пользователи") шапка с крестиком закрытия и кнопка
"Выйти" уезжали вместе с контентом за пределы экрана и становились
недостижимы без скролла назад. Исправлено разделением на три flex-блока
внутри `.sidebar` (`display:flex;flex-direction:column`):
`.sidebar-top` (лого+крестик) и `.logout-btn` — `flex:0 0 auto`,
зафиксированы; между ними `.sidebar-scroll` (обёртка вокруг `.nav-list` +
ссылок "Админ"/"Пользователи", добавлена в `renderMenu()` в
components.js) — `flex:1 1 auto; overflow-y:auto`, скроллится только он.
Работает только в мобильном `@media`-блоке — на десктопе `.sidebar` не
скроллится вовсе (всё и так помещается), `.sidebar-scroll` там обычный
блок без `overflow`. Тонкий скроллбар для `.sidebar-scroll` — тот же
паттерн, что у `.log`/`#roomList` (секция "SCROLLBARS" в styles.css).

**Регрессия от этого же фикса (важно на будущее).** Изначально
`min-height: 0` на `.sidebar-scroll` был в БАЗОВОМ (не мобильном) правиле.
На десктопе, если окно невысокое (админ залогинен → сайдбар длиннее
окна), это давало flex-shrink право сжать `.sidebar-scroll` НИЖЕ высоты
его реального контента (у flex-item `min-height` по умолчанию `auto` =
"не меньше контента", `min-height:0` явно снимает эту защиту) — сам блок
сжимался, а его дети (nav-admin/nav-users) вылезали за пределы уже
сжатого блока и налезали на "Выйти", который позиционировался по краю
сжатого (а не настоящего) блока. Итог — пункты меню накладывались друг на
друга. Фикс: `min-height: 0` должен быть ТОЛЬКО внутри мобильного
`@media`-блока (он там обязателен — без него `flex:1 1 auto` +
`overflow-y:auto` не сработает, т.к. блоку не разрешат сжаться под
скролл), на десктопе `.sidebar-scroll` не должен его иметь вообще.
Общий урок: `min-height: 0` на flex/grid-item — всегда обдуманно решай,
для какого именно breakpoint'а он нужен, не добавляй "на всякий случай"
в базовое правило.

**Скролл сайдбара на десктопе.** После фикса выше пункты меню на
десктопе перестали накладываться друг на друга, но на невысоком окне
(особенно с "Админ"/"Пользователи" для админа) низ списка всё ещё
обрезался viewport'ом без возможности докрутить — на десктопе `.sidebar`
не выезжающая панель, просто узкая колонка слева, и раньше у неё не
было `overflow`. Добавлено `overflow-y: auto` прямо в БАЗОВОЕ правило
`.sidebar` (styles.css, самое начало) — работает только когда контент
реально не помещается (обычно не видно, скроллбар не мешает). В мобильном
`@media`-блоке это перекрывается обратно в `overflow: hidden`, т.к. там
скроллится внутренний `.sidebar-scroll`, а не сам `.sidebar` (см. выше) —
если меняешь `.sidebar` overflow, не забывай про этот override ниже по
файлу. Тонкий скроллбар — та же секция "SCROLLBARS", `.sidebar` добавлен
туда третьим селектором рядом с `.sidebar-scroll`.

**Резкая граница фона на коротких мобильных страницах.** `body` красится
радиальными градиентами, угасающими к центру ("45%"), привязанными к
своим же верхнему левому/нижнему правому углу. На мобильном `body` —
`height:auto` (для обычного скролла страницы вместо десктопного
`overflow:hidden` с внутренним скроллом `.app`), поэтому на странице с
малым количеством контента (мало постов и т.п.) блок `body` короче
экрана — градиент угасает в пределах своих ~400px, ниже видна только
плоская заливка `var(--bg)`, и получается резкая горизонтальная граница
посередине экрана. Исправлено — `body { min-height: 100vh; min-height:
100dvh; }` внутри мобильного `@media`-блока, чтобы фон всегда был минимум
на весь экран независимо от длины контента (для контента ДЛИННЕЕ экрана
ничего не меняется — `height:auto` всё так же даёт странице расти дальше
и скроллиться).

## Друзья (`friends.html`) — вкладки + подписки

Поиск теперь один блок сверху страницы (без заголовка "Найти человека"),
под ним вкладки: **Друзья** / **Заявки** (бывшие "Входящие заявки") /
**Подписки**. Переключение вкладок — чисто клиентское (`initFriendsPage()`
в app.js: `.tab-btn` клик прячет/показывает соответствующий `<div
id="friends...List">` через атрибут `hidden`; данные для всех трёх вкладок
подгружаются сразу при заходе на страницу, не лениво по клику).

**Подписки** = мои исходящие заявки в друзья, которые ещё не приняты
(`friendships.status='pending' AND requestedBy=я`) — семантика "я
подписан, но не факт что взаимно", как в ВК 2010. Новый роут `GET
/api/friends/subscriptions` + `stmts.listOutgoingRequests` в server.js
(зеркало уже существовавшего `listIncomingRequests`, но
`f.requestedBy = ?` вместо `<>`). Отписаться = тот же `POST
/api/friends/decline/:userId`, что уже использовался для отклонения
входящей заявки и удаления друга — он просто удаляет строку `friendships`
независимо от направления, поэтому отдельный роут не понадобился.
Технически подписка не даёт никакого отдельного доступа к контенту —
стены и так публичны для любого залогиненного (см. пункт выше про
сознательные упрощения) — это просто список "кого я хочу видеть в
друзьях, но пока в одну сторону", а не механизм контроля доступа.
Блокировки пользователей (чтобы подписка/видимость реально что-то
ограничивала) в проекте нет — если понадобится, это отдельная фича
(таблица `blocks`, проверка в `requireAuth`/при рендере стены).

**Важно про `[hidden]`**: после того, как на эту же грабли наступили уже
трижды (`#preview`, `.moderation-reason`, теперь `.person-list` с
`display:flex`), добавлено глобальное защитное правило `[hidden] {
display: none !important; }` в начале styles.css. Теперь НЕ нужно
подбирать `width:fit-content` вместо `display` для новых элементов,
которые прячутся через `hidden`, — правило само гарантирует, что `hidden`
побеждает любой `display` от класса. Если увидишь элемент с `hidden`,
который всё равно видим, — это правило либо отсутствует, либо
переопределено более специфичным/поздним `!important`-правилом.

## Чаты (`chats.html`) — список диалогов в стиле ВК

По референсам (скриншоты старого ВК-десктопа + мобильного клиента):
сначала выбираешь диалог из списка, потом переписываешься внутри него.

- **Список диалогов** (`renderRoomsList()` в app.js) — теперь не просто
  текст, а строка `.room-item`: аватар (`.room-avatar`, фото или первая
  буква названия), имя + превью последнего сообщения (`.room-preview` —
  "Вы: текст" если последнее сообщение моё, иначе просто текст; "Вложение"
  если это файл без текста), время справа (`.room-time` —
  `formatRoomTime()`: часы:минуты если сегодня, иначе "3 июл"). Данные
  берутся из уже существующего локального кэша сообщений
  (`loadMessages(roomId)` — последний элемент массива), новых полей в БД
  не добавлялось. Превью обновляется на КАЖДОЕ сообщение (не только для
  новых комнат) — `renderRoomsList()` теперь вызывается безусловно в WS
  `message`-хендлере (server.js тут ни при чём, это чисто клиентский кэш).
- **Мобильный полноэкранный режим** — на `≤768px` список и сам чат больше
  не стоят друг под другом (как было раньше), а показываются по одному,
  как два "экрана": класс `.chat-open` на `.chat-layout` переключает
  видимость (`renderRoomsList()` добавляет класс по клику на диалог,
  `#chatBackBtn` — кнопка со стрелкой в шапке чата, видна только на
  мобильном — его убирает). На десктопе класс `.chat-open` ничего не
  меняет, обе колонки всегда видны рядом (grid, как раньше).
- Порядок при открытии страницы: `.chat-open` не выставлен по умолчанию —
  на мобильном всегда сначала виден список (как на референсе), даже
  если `currentRoom`/сообщения уже отрендерены в фоне в скрытый
  `.chat-main`.
- **Создание комнаты — БЕЗ `prompt()`.** Раньше "+ Комната" вызывала
  нативный `window.prompt()` — в части окружений/браузеров такие
  диалоги вообще не показываются (тихо возвращают `null`), кнопка
  выглядела нерабочей. Теперь по клику раскрывается обычная инлайн-форма
  (`#addRoomForm`, input + "Создать") под кнопкой — тот же паттерн, что
  везде в проекте (создание группы/альбома). На мобильном после создания
  комнаты `.chat-open` выставляется автоматически, как и при клике на
  диалог в списке. **Урок**: в этом проекте НЕ используй `alert`/`confirm`/
  `prompt` для чего-либо важнее одноразового уведомления — они не
  тестируются автоматизацией (см. более ранние заметки про `confirm()`
  при удалении) и могут быть недоступны части реальных пользователей;
  всегда инлайн-форма или кастомный тост/баннер (`confirm()` для
  подтверждения ОПАСНОГО действия типа удаления — это ок и так уже
  сделано во всём проекте, эта рекомендация конкретно про `prompt()`
  для ввода данных).

**Шапка чата — счётчик "в сети" и меню-троеточие (как в телеграме).**
- `broadcastPresence(room)` в server.js — считает реальное число РАЗНЫХ
  логинов, сейчас подключённых к комнате (`clients` Set, WS), и шлёт всем
  в этой комнате `{type:"presence", room, count}` при каждом
  подключении/отключении кого-либо. Это НЕ "участники беседы" в смысле
  членства — такой сущности в модели чата нет (комната это просто строка,
  подключиться может кто угодно, знающий её id) — а честный live-счётчик
  "сколько человек прямо сейчас смотрит в этот чат". Клиент:
  `updateRoomPresence(count)` в app.js пишет "N в сети" в
  `#chatHeaderSubtitle`, вызывается из WS-хендлера на `msg.type ===
  "presence"`, только если `msg.room === currentRoom`. `setStatusOnline()`
  теперь дёргается только при обрыве соединения (пишет "нет соединения") —
  при удачном коннекте текст не трогает, ждёт presence, чтобы не мелькала
  неточная надпись перед реальным числом.
- Кнопка `#chatMenuBtn` (иконка `moreVertical`) открывает
  `#chatMenuDropdown` — содержимое СОБИРАЕТСЯ ДИНАМИЧЕСКИ в
  `renderChatMenu()` (app.js), вызывается из `updateChatHeader()` при
  каждой смене чата, т.к. набор пунктов разный для комнаты/группы и для
  личного диалога (`currentRoom.startsWith("dm-")`). Открытие/закрытие —
  клик по кнопке (`stopPropagation`) + клик где угодно ещё в документе
  закрывает; клик внутри дропдауна тоже не всплывает (иначе глобальный
  обработчик закрывал бы его раньше, чем сработает пункт).
  - **Оба типа**: Включить/Выключить уведомления (`room.muted` в
    `roomsLocal`, проверяется в WS-хендлере перед `tryShowNotification`),
    Экспорт истории чата (скачивает `.txt` из уже закэшированной локально
    истории — `downloadTextFile()`, реальный `Blob`+`<a download>`, не
    требует сервера), Очистить историю (чистит ТОЛЬКО локальный кэш этого
    устройства — `saveMessages(id, [])`, серверная история комнаты не
    трогается, т.к. общего "удалить у всех" смысла в личной команде нет),
    Удалить чат/Удалить и покинуть (было и раньше — вынесено в
    `deleteCurrentRoom()`).
  - **Только для DM**: Показать профиль (`getDmPeerId()` вычисляет id
    собеседника из самого roomId `dm-<a>-<b>` — id не содержат дефисов,
    поэтому парсинг простой `slice(3).split("-")`), Установить/Изменить
    обои (`room.wallpaperUrl`, кладётся фоном на `#log` через
    `applyWallpaper()`, обычная ссылка на картинку, без загрузки файла),
    Запретить/Разрешить копирование (`room.copyDisabled` →
    `applyCopyProtection()`: класс `.no-copy` = `user-select:none` +
    `#log.oncopy = e=>e.preventDefault()`; это чисто клиентская
    "вежливая" мера, а не защита от копирования — любой человек с devtools
    её обойдёт, как и в самом телеграме).
  - **Группы/комнаты (не DM) — все пункты в итоге реализованы по
    просьбе пользователя** (изначально были осознанно пропущены как
    "нет подходящей сущности", затем добавлены полноценно):
    - **Информация о группе** (`showGroupInfo()`) — название/создатель/
      дата создания с сервера (если карточка зарегистрирована, см. ниже),
      либо честная заглушка "Общая комната (без владельца)" для комнат
      без карточки (`public`), плюс всегда — число сообщений в локальном
      кэше на этом устройстве. Никаких выдуманных цифр.
    - **Управление группой** (`showGroupManage()`/`saveGroupManage()`) —
      переименование + ссылка на аватар, реально применяется у ВСЕХ, кто
      подключён к комнате (WS `roomUpdate`), не только у автора действия.
      Требует таблицу `chat_rooms` (id, name, avatarUrl, ownerId,
      createdAt) в db.js — "карточка" поверх комнаты, которая физически
      остаётся просто строкой для WS. Комната регистрируется на сервере
      автоматически при создании через "+ Комната" (`POST
      /api/chat-rooms`, best-effort — если не получилось, комната всё
      равно работает как обычный WS-канал, просто без этих двух пунктов
      меню). `PATCH /api/chat-rooms/:id` — только владелец или админ.
    - **Создать опрос** (`showPollForm()`/`createPollFromForm()`) —
      настоящий опрос: вопрос + 2-10 вариантов, голос рассылается всем в
      комнате в реальном времени (WS `type:"poll"` на создание,
      `type:"vote"` на голос, `type:"pollUpdate"` — рассылка результата).
      Хранится в `messages.pollData` (TEXT/JSON) — опрос это ОБЫЧНОЕ
      сообщение с пустым `text` и заполненным `pollData`, а не отдельная
      сущность. Голосование одиночное (голос переносится в новый вариант
      при повторном клике). `toMessagePayload()` теперь также отдаёт `id`
      сообщения (раньше не отдавал вообще — клиенту нечем было бы
      ссылаться на конкретное сообщение для голосования).
    - **Создать список** — сообщение-чеклист (список задач с чекбоксами)
      ВНУТРИ чата, не папка для организации диалогов (это уточнил
      пользователь отдельно — первая реализация была про группировку
      диалогов в сайдбаре и была заменена на эту). Модель — та же, что у
      опросов: `messages.checklistData` (TEXT/JSON), WS `type:"checklist"`
      на создание, `type:"checklistToggle"` на клик по галочке,
      `type:"checklistUpdate"` — рассылка всем в комнате. Ключевое отличие
      от опроса: каждый пункт — НЕЗАВИСИМАЯ галочка, которую может
      поставить/снять ЛЮБОЙ участник (общее состояние, не "мой голос") —
      клик всегда переключает `item.checked`, `item.checkedBy` = кто
      отметил последним (или `null`, если сняли). `checkedBy` — это
      display name (`displayNameOf()`), НЕ login — легко напутать по
      аналогии с `poll.options[].votes`, которые хранят логины (там ок,
      потому что наружу показывается только количество, а не сами логины).
      `renderChecklistBlock()`/`toggleChecklistItem()`/`updateChecklistUI()`
      в app.js — зеркалят `renderPollBlock()`/`voteOnPoll()`/`updatePollUI()`.
    - **Трекер времени на пункте списка** ("сколько у кого времени ушло") —
      `item.timers` внутри того же `checklistData`: массив `{ login,
      displayName, totalSeconds, runningSince }`, по одной записи на
      каждого, кто хоть раз нажал "Трекер" на этом пункте. WS
      `type:"checklistTimerToggle"` — старт/стоп персонально для того, кто
      нажал (у каждого свой независимый таймер на одном и том же пункте,
      не общий на всех). Стоп считает `totalSeconds += (Date.now() -
      runningSince) / 1000` и обнуляет `runningSince`; старт просто
      выставляет `runningSince = Date.now()`. `runningSince` —
      АБСОЛЮТНЫЙ серверный timestamp, поэтому "сколько идёт прямо сейчас"
      каждый клиент честно досчитывает сам (`Date.now() - runningSince`)
      без рассинхрона часов между устройствами.
      Живой тикающий счётчик — ОДИН общий `setInterval` на всю страницу
      (`startChecklistTicker()`, стартует один раз в `initChatPage()`), а
      не по интервалу на каждый список/пункт — каждую секунду ищет все
      видимые `.checklist-timer-breakdown[data-has-running="true"]` и
      перерисовывает их из локального кэша сообщений (`loadMessages`),
      который уже обновляется на каждый `checklistUpdate` по WS. Если
      открыто несколько списков с активными таймерами одновременно — все
      тикают от одного и того же интервала, лишних таймеров не плодится.
    - **Пожаловаться** (`sendReportFromForm()`) — новая таблица
      `chat_reports` (id, room, reporterId, note, createdAt), `POST
      /api/chat-reports`. Админка: секция "Жалобы на переписку" в
      admin.html (`renderAdminChatReports()`) — `GET/DELETE
      /api/admin/chat-reports`, кнопка "Отметить рассмотренной" просто
      удаляет запись (без статусов "открыта/закрыта" — MVP).

**Анимация сворачивания — доработана (изначальная версия дёргалась).**
Проблема была в двух местах: (1) подписи пунктов прятались через
`display:none` — исчезали/появлялись МГНОВЕННО, пока сама колонка
`.sidebar` ещё плавно анимировала `width`, из-за чего разворот выглядел
рывком, а не одной анимацией; (2) центрирование иконки в свёрнутом виде
делалось через `justify-content:center` — это скачкообразное свойство
(браузер физически не умеет его анимировать/интерполировать), иконка
мгновенно "прыгала" в центр строки. Исправлено:
- Разметка в `renderMenu()` (components.js) теперь оборачивает иконку и
  подпись в отдельные `<span class="nav-icon">`/`<span class="nav-label">`
  (было — голый `<span>` только вокруг подписи). `.nav-icon` —
  fixed-width (18px) обёртка, поэтому иконка НИКОГДА не двигается сама
  по себе при сворачивании/разворачивании.
- `.nav-label`/`.logo-text` вместо `display:none` теперь анимируются
  через `max-width` + `opacity` (transition на оба свойства) — подпись
  плавно сжимается и растворяется синхронно с шириной сайдбара, а не
  исчезает скачком.
- Центрирование иконки в свёрнутом виде — теперь через симметричный
  `padding-left/right:17px` на строке пункта (вместо `justify-content`),
  который, в отличие от `justify-content`, браузер честно анимирует
  вместе с шириной колонки.
- `.sidebar` transition — `width` + `padding` на `cubic-bezier(.4,0,.2,1)`
  0.25s (было просто `width .2s ease`) — чуть плавнее и покрывает оба
  меняющихся свойства.
- Заодно: `.logo-circle` (лого "LÖ", по которому кликают, чтобы
  свернуть/развернуть) получил `cursor:pointer` в БАЗОВОМ правиле — до
  этого курсор был `pointer` только в свёрнутом состоянии, хотя кликать
  можно в обоих.

**[БАГ-ФИКС] История чата с сервера никогда не отображалась.**
`wss.on("connection", ...)` в server.js всегда честно шлёт
`{type:"history", data:[...]}` (последние 50 сообщений комнаты) сразу
после подключения — но клиентский WS-обработчик в app.js
(`connectWebSocket()`) проверял только `"presence"`/`"roomUpdate"`/
`"pollUpdate"`/`"checklistUpdate"`/`"system"`/`"chat"` — тип `"history"`
никогда не обрабатывался и молча игнорировался. На практике это
означало: реальная история чата существовала в БД, но новый человек
(или чужой браузер/устройство без локального кэша — вся история чата
на клиенте держится в `localStorage`, см. `loadMessages`/`saveMessages`)
не видел вообще НИЧЕГО из прошлой переписки, пока не получал сообщения
"живьём" по WS уже будучи подключённым. Баг всплыл при создании тестового
аккаунта "Иван Петров" и переписке с админом — админ открыл диалог и
увидел пустой чат, хотя сообщение точно было отправлено и сохранено.
Исправлено — добавлен обработчик `msg.type === "history"`: мержит
`msg.data` с уже сохранённым локальным кэшем комнаты по `id` сообщения
(не затирает кэш целиком), при необходимости заводит локальную карточку
комнаты в `roomsLocal` (если открыли диалог впервые на этом устройстве,
например по ID, и сами ещё ничего не писали), перерисовывает список
диалогов и текущий лог. Затрагивает вообще ВСЕ комнаты/диалоги, не
только новые — то есть любой открытый впервые на новом устройстве чат
теперь наконец подтягивает реальную историю с сервера, а не только то,
что было получено "живьём".

**Переработан рендер сообщений чата — аватар/имя по контексту,
раскладка по ширине окна.** Раньше КАЖДОЕ сообщение (и своё, и чужое)
показывало подпись "Имя, время" и декоративный кружок-аватар (через
CSS `::before`, `--avatar-url` custom property), а сами сообщения
всегда шли одной колонкой на всю ширину `#log`. По референсам
(скриншоты Telegram) переделано на структуру `.msg-row` →
`.msg-avatar` (опционально) + `.msg-bubble` (`appendMessageToLog()` в
app.js, `data-message-id` теперь на `.msg-bubble`, а не на строке —
`updatePollUI()`/`updateChecklistUI()` ищут по этому атрибуту и
дописывают опрос/чек-лист туда же, они не менялись).

Кто получает аватар/имя — зависит ТОЛЬКО от того, чьё сообщение и
личный это диалог или комната, но НЕ от ширины экрана:
- своё сообщение (`isMe`) — никогда ни аватара, ни имени (понятно и
  так, по цвету/выравниванию);
- чужое в личном диалоге (`currentRoom.startsWith("dm-")`) — аватар
  есть, имени нет (собеседник один, он и так виден в шапке чата);
- чужое в комнате/группе — аватар И имя (отправителей несколько,
  нужно различать, кто есть кто).
Аватар при этом рендерится, только если у конкретного сообщения есть
снимок `avatar` (см. выше про снимок на момент отправки) — старые
сообщения без него по-прежнему честно показывают имя без кружка,
никаких выдуманных аватарок.

Время сообщения (`.msg-time`) — отдельный элемент, ВСЕГДА внизу пузыря
прижат вправо (`text-align:right`), а не сверху рядом с именем, как
было раньше (единый `.meta` с текстом `"Имя, время"`). Имя (если
показывается по правилам выше) осталось отдельной строкой сверху
пузыря (`.meta`, теперь содержит только имя, без времени). Работает
одинаково при любой ширине экрана — вниз-вправо время уходит и в
колонке (≥1200px), и в пузыре (<1200px).

Раскладка ("друг под другом одной колонкой" vs "пузыри друг напротив
друга, свои справа") зависит ТОЛЬКО от ширины окна — новый брейкпоинт
**1200px**, специально заведённый ОТДЕЛЬНО от основного мобильного
768px (тот двигает сайдбар/переключение списка↔чата на телефоне, к
рендеру самих сообщений отношения не имеет):
- `≥1200px` — `.msg-bubble` растягивается на всю ширину строки
  (`flex:1 1 auto`), сообщения идут одной колонкой, как раньше;
- `<1200px` (`@media (max-width: 1199.98px)` в styles.css) —
  `.msg-bubble` получает `max-width:78%`, `.msg-row.me` —
  `justify-content:flex-end` (свои вправо), у чужих остаётся
  `flex-start` (по умолчанию) — итого пузыри как в обычном мессенджере.
  Это НЕ переопределяет то, что видно, только то, КАК это расположено —
  на <1200px в комнате по-прежнему видно и аватар, и имя, просто в
  виде пузыря, а не строки на всю ширину.

**Открытый чат на мобильном — теперь настоящий полноэкранный "локальный"
режим, растянутый на всю высоту.** Раньше `.chat-main` на мобильном был
`height:auto` внутри обычного скроллящегося потока страницы (нужного
другим мобильным страницам — там `body{height:auto;overflow:auto}`),
а `#log` был жёстко ограничен `max-height:55vh` — из-за этого под чатом
оставался пустой "хвост" страницы, а сам чат не занимал реально видимую
высоту экрана. Теперь `.chat-layout.chat-open` (мобильный `@media`) —
`position:fixed; inset:0;` поверх ВСЕЙ страницы, включая обычную шапку
(хамбургер/заголовок/тема) — она специально перекрывается, а не просто
остаётся сверху: у чата уже есть свой хедер с кнопкой "назад", второй
хедер был бы лишним (как в телеграме/whatsapp). `#log` больше не имеет
`max-height:55vh` — вернулся к обычному `flex:1 1 auto` (из базового,
некопированного мобильного правила), поэтому честно тянется на всю
доступную высоту между хедером чата и полем ввода.

Высота берётся из CSS-переменной `--app-vh` (не `100vh`/`100dvh`
напрямую) — `initMobileChatViewport()` в app.js подписывается на
`window.visualViewport.resize` и пишет туда `visualViewport.height`.
Это принципиально: на iOS Safari открытие экранной клавиатуры НЕ
меняет layout viewport (от которого считаются `vh`/`dvh`) — чат на
`100dvh` просто оказался бы наполовину под клавиатурой. `visualViewport`
— единственный API, честно отражающий видимую (не перекрытую
клавиатурой) область на всех современных мобильных браузерах, и его
`resize` событие срабатывает и при открытии/закрытии клавиатуры, и при
повороте экрана. Функция вызывается безусловно в `DOMContentLoaded`
(как `initMobileMenu()`) — на десктопе `--app-vh` тоже выставляется, но
ни на что не влияет, т.к. используется только внутри
`.chat-layout.chat-open` в мобильном `@media`-блоке.

## Звонки (аудио через WebRTC)

Первая версия — только аудио, только 1-на-1 (личный диалог); видео и
групповые звонки — осознанно не в этом заходе (см. ниже).

- **Сигналинг** — `server.js`, новые типы WS-сообщений `call-offer`/
  `call-answer`/`call-ice`/`call-reject`/`call-end`/`call-busy` в
  общем `ws.on("message", ...)` (там же, где `chat`/`poll`/`checklist`).
  Сервер НЕ участвует в самом голосе — только пересылает служебные
  SDP/ICE-сообщения от одного пользователя к другому, находя получателя
  по `login` (а НЕ по `room` — звонок не привязан к тому, какая комната
  у кого открыта в WS, это независимая вещь). `from`/`fromDisplayName`/
  `fromAvatar` сервер всегда подставляет сам из `client.login` (текущего
  WS-соединения), не доверяя телу сообщения — звонящий не может выдать
  себя за другого. Если получатель ни к чему не подключён — звонящему
  честно летит `call-unavailable` вместо вечных гудков в пустоту.
- **Клиент** — `app.js`, секция "ЗВОНКИ (аудио через WebRTC)" перед
  `connectWebSocket()`. `activeCall` — единственный глобальный объект
  состояния звонка (`callId`, `peerLogin`, `pc` — RTCPeerConnection,
  `localStream`, `status`: `outgoing`/`incoming`/`connected`/`ended`).
  UI — `renderCallOverlay()`, оверлей создаётся прямо в JS (как
  `openPhotoLightbox()`), а НЕ часть разметки chats.html — поэтому
  входящий звонок виден на ЛЮБОЙ странице (WS глобальный, см.
  `connectWebSocket()`), не только в чатах. `handleCallSignal()` —
  диспетчер входящих `call-*` сообщений, подключён в общем WS-обработчике
  через `CALL_MESSAGE_TYPES`.
  ICE-кандидаты, пришедшие раньше `setRemoteDescription` (обычная гонка
  в WebRTC) — складываются в `activeCall.pendingCandidates` и
  применяются после того, как remote description выставлен (логика
  общая что для звонящего, что для принимающего).
- **Кнопка звонка** — `#chatCallBtn` в шапке чата (`chats.html`), рядом
  с кнопкой-троеточием; видимость переключает `updateChatHeader()` —
  только для `dm-*`-комнат (`hidden` для комнат/групп, групповых звонков
  нет). Значок и обработчик клика вешаются один раз в `initChatPage()`
  (обычный паттерн этого файла — один слушатель на всю жизнь страницы,
  не перевешивается на каждую смену чата).
- **STUN, без TURN** — `CALL_ICE_SERVERS` в app.js, только публичный
  Google STUN. Работает в подавляющем большинстве сетей (обычный
  домашний/мобильный NAT), но за особо строгим NAT (часть корпоративных
  сетей, symmetric NAT) соединение может не установиться — для железной
  гарантии везде нужен свой или платный TURN-сервер, это отдельная
  инфраструктурная штука (не просто конфиг), сознательно не в этом
  заходе.
- **Ограничение архитектуры (осознанное, важное).** Проект
  многостраничный (обычные переходы между `.html`, НЕ SPA) — значит
  `RTCPeerConnection` физически не переживает переход на другую страницу
  (вся JS-память уничтожается браузером при навигации, как при обычной
  перезагрузке). `beforeunload` в app.js best-effort шлёт `call-end`
  собеседнику при уходе со страницы посреди разговора (чтобы у него не
  остался зависший "идёт разговор"), но сам звонок в любом случае
  обрывается — рассчитано, что говорить будут, оставаясь на одной
  странице (chats.html), как и будет в подавляющем большинстве случаев.
- **Иконки** — добавлены `call` (трубка), `mic`/`micOff` в
  `ICON_PATHS` (components.js). Кнопки "отклонить"/"сбросить" — та же
  иконка `call`, развёрнутая на 135° через CSS (`.call-btn-end svg`) —
  стандартный визуальный приём "положить трубку", отдельная иконка не
  понадобилась.
- **Проверено:** UI всех состояний (исходящий/входящий/отклонён),
  реальный round-trip через сервер (`call-offer` → относится по login,
  `from*` честно подставлены сервером), путь "собеседник не в сети"
  (`call-unavailable`), корректная очистка состояния после звонка.
  Реального сквозного аудио между двумя живыми людьми проверить не
  удалось — у автоматизированного браузера в этом окружении нет
  доступа к микрофону (`getUserMedia` заблокирован), и это ожидаемо
  ловится кодом (`"Нет доступа к микрофону"`), не роняя ничего. Логика
  `RTCPeerConnection`/`getUserMedia` — стандартные, широко
  использующиеся браузерные API; корректность самого голоса стоит
  проверить на двух настоящих устройствах с микрофоном при первой
  возможности.

**Следующий шаг (не сделан):** видеозвонки — тот же сигналинг уже
поддерживает флаг `video` в `call-offer`, останется добавить
`getUserMedia({video:true})`, `<video>`-элементы для локального/
удалённого потока и переключение "аудио/видео" в UI кнопки звонка.

## PWA — устанавливается на телефон ("Добавить на главный экран")

Первый шаг к мобильному приложению — не нативный APK, а PWA
(Progressive Web App): телефон предлагает установить сайт как обычное
приложение (иконка на главном экране, отдельное окно без адресной
строки браузера, `theme_color` красит системную шторку). Настоящий
`.apk`-файл — следующий, отдельный шаг поверх этого (см. ниже).

- **`manifest.json`** (корень проекта) — имя, иконки, `display:
  standalone`, `theme_color: #16a34a` (тот же зелёный, что у бренда),
  `start_url: /index.html`. Подключён `<link rel="manifest"
  href="manifest.json">` во ВСЕХ 14 HTML-страницах (плюс `<meta
  name="theme-color">` и `<link rel="apple-touch-icon">` — iOS манифест
  умеет далеко не всё, apple-touch-icon нужен отдельно).
- **`icon-192.png`/`icon-512.png`** — сгенерированы программно (canvas
  в браузере: тот же радиальный градиент и стиль "LÖ", что у
  `.logo-circle` в styles.css, см. историю сессии — временная HTML-
  страница с `<canvas>` рисовала иконку, дальше PNG сохранён на диск
  через ВРЕМЕННЫЙ dev-роут в server.js, роут и страница удалены сразу
  после использования, ничего постоянного не осталось).
- **`sw.js`** (service worker, корень проекта) — минимальный, нужен
  прежде всего для критерия "устанавливаемости" (Chrome требует хотя бы
  один `fetch`-обработчик у SW). Кэширует только статическую ОБОЛОЧКУ
  (`styles.css`/`app.js`/`components.js`/иконки) по стратегии
  "сеть в приоритете, кэш — запасной вариант при обрыве связи". `/api/*`
  и не-GET запросы НЕ кэшируются никогда — посты/сообщения/друзья
  обязаны быть свежими, а не залежавшимся снимком. Регистрируется в
  app.js (`navigator.serviceWorker.register("/sw.js")`, после
  `window.load`) — один блок кода в самом начале файла, работает на
  всех страницах.
- Все 4 новых файла (`manifest.json`, `sw.js`, `icon-192.png`,
  `icon-512.png`) добавлены в `PUBLIC_FILES` в server.js — тот же
  allowlist-механизм, что у остальной статики (иначе 404-ились бы).

**Что дальше, если понадобится настоящий `.apk` (отдельный шаг, не
сделан):** сайт нужно сначала задеплоить на реальный публичный
HTTPS-домен (localhost не подходит — по правилам проекта деплой только
с явного разрешения, см. "Что НЕ делать без явного разрешения" ниже),
после чего бесплатный сервис PWABuilder.com (или CLI Bubblewrap)
оборачивает уже готовую PWA в подписанный `.apk`/`.aab` без переписывания
кода — ту же PWA-разметку, что уже есть.

## [БАГ-ФИКС] API_URL/WS_URL ломались при заходе не через localhost

`app.js` раньше хардкодил: если `window.location.hostname` не ровно
`"localhost"`/`"127.0.0.1"` — считать это продакшеном и стучаться на
`https://lyomo-1.onrender.com` (старый, давно не обновлявшийся деплой).
Из-за этого при заходе на дев-сервер по IP в локальной сети (например, с
телефона на `http://192.168.x.x:4000` для проверки PWA-установки —
см. раздел "PWA" выше) `window.location.hostname` был IP-адресом, не
входящим в этот список, — приложение молча слало все API/WS-запросы на
чужой нерабочий Render вместо реального локального сервера. Регистрация
(и вообще всё) в такой сессии просто ничего не делала.

`server.js` в этом проекте ВСЕГДА отдаёт и фронтенд, и API с одного и
того же origin (никогда не были разнесены на разные хосты, несмотря на
старый комментарий "в проде фронтенд может быть захостен отдельно") —
поэтому `API_URL`/`WS_URL` теперь просто всегда текущий адрес страницы
(`window.location.protocol/host`), без каких-либо условий и хардкода
конкретного домена. Работает одинаково на `localhost`, по IP в локальной
сети и на любом реальном домене после деплоя.

диалог не появится в списке сам по себе, пока получатель не откроет его
хотя бы раз (по ссылке `?peer=` или через поиск по ID) — реального

писал, нет (WS привязан к одной конкретной комнате на соединение, см.
"Друзья" раздел выше и известную проблему #3 про JWT на WS).

## [ФИКС] Явный `play()` для звонка — иначе иногда "соединилось", но не слышно

`pc.addEventListener("track", ...)` в `createCallPeerConnection()` (app.js)
создавал `<audio autoplay>` и просто выставлял `srcObject` — на десктопном
Chrome этого обычно достаточно, но на части мобильных браузеров (особенно
iOS Safari) один атрибут `autoplay` ненадёжен даже после пользовательского
жеста, которым был начат звонок: воспроизведение может не запуститься само,
и получается ситуация "звонок прошёл, но собеседника не слышно". Добавлены
`audioEl.playsInline = true` и явный `audioEl.play().catch(...)` сразу после
установки `srcObject`.

**Если после этого фикса звук всё ещё не проходит** — вероятная причина
другая и эту функцию не чинит: в проекте только STUN (`CALL_ICE_SERVERS`,
публичный Google STUN), TURN-сервера нет (см. раздел "Звонки" выше — это
осознанный компромисс, TURN нужен отдельной инфраструктурой). Если оба
собеседника (или один из них) — за NAT, который STUN не пробивает
(распространено на мобильных операторах с CGNAT, части корпоративных
сетей), ICE-соединение для самого медиапотока просто не установится, даже
если сигналинг (обмен offer/answer через сервер) прошёл полностью и UI
показывает "звонок идёт". Проверить: `activeCall.pc.connectionState` в
консоли браузера во время звонка — если не `"connected"`, дело в этом, и
единственное реальное решение — подключить TURN (например, Metered.ca,
Twilio STUN/TURN или свой coturn — платная или требующая настройки
инфраструктура, не сделано без отдельного решения пользователя).

## [БАГ-ФИКС] Звонок показывал "разговор идёт" (таймер тикает), а звука не было

По прямой жалобе пользователя ("всё ещё не слышу собеседника когда звоню").
Разбор кода `createCallPeerConnection()`/`startCall()`/`acceptCall()`/
`handleCallSignal()` в app.js и релея сигналов в server.js не показал
проблем с самим WebRTC-обменом (offer/answer/ICE передаются корректно) —
баг был не в сигналинге, а в UI-состоянии звонка и в перерисовке оверлея.

**Баг 1 — статус "connected" выставлялся СРАЗУ после обмена SDP, а не
после реального подключения.** И `acceptCall()`, и обработчик
`call-answer` в `handleCallSignal()` ставили `activeCall.status =
"connected"` и стартовали таймер сразу, как только собеседник ответил на
сигнальном уровне — а не когда `pc.connectionState` в WebRTC реально
становился `"connected"`. Из-за этого таймер тикал и UI показывал
"разговор идёт", даже если ICE-соединение для самого медиапотока ещё не
установилось (или не установится вообще — см. "[КРИТИЧНО]" про TURN
чуть выше). Пользователь видел идущий звонок и тишину и не мог понять,
это баг или ещё не подключилось. Добавлен отдельный промежуточный
статус `"connecting"` ("Соединяем...") — в `"connected"` теперь
переводит ТОЛЬКО реальный `connectionstatechange` на `pc` (см.
`createCallPeerConnection()`), когда `pc.connectionState === "connected"`.
Заодно исправлен сам обработчик `connectionstatechange`: раньше `failed`/
`disconnected` завершали звонок (`endCall()`) только если статус уже был
`"connected"` — если ICE вообще не мог подключиться, `pc.connectionState`
никогда не становился `"connected"`, поэтому и `"failed"` никогда не
ловился, и звонок молча зависал на "Соединяем..." навсегда. Теперь
`failed`/`disconnected` завершает звонок и из статуса `"connecting"` —
`"Не удалось установить соединение"` вместо вечного зависания.

**Баг 2 — куда серьёзнее, ЛОМАЛ ЗВУК ДАЖЕ ПРИ РЕАЛЬНОМ ПОДКЛЮЧЕНИИ.**
`renderCallOverlay()` (перерисовывает карточку звонка при каждой смене
статуса — outgoing → connecting → connected) в начале вызывала
`removeCallOverlay()`, которая удаляла не только саму визуальную
карточку, но и `#callRemoteAudio` — `<audio>`-элемент с входящим звуком
собеседника. А `#callRemoteAudio` создаётся и получает `srcObject` ОДИН
РАЗ, по событию `"track"` на `RTCPeerConnection` (см.
`createCallPeerConnection()`) — которое по спецификации WebRTC может
сработать раньше, чем агрегированный `pc.connectionState` реально
станет `"connected"` (RTP/медиа может пойти сразу после DTLS-хендшейка,
это происходит примерно в то же время, что и переход в `"connected"`,
но не строго после него). Итог: если `track` успевал сработать (звук
реально начинал играть) ДО того, как `connectionstatechange` перерисовывал
UI в статус "connected" — эта перерисовка тут же удаляла уже играющий
`<audio>` из DOM, и звук молча обрывался. Собеседника переставало быть
слышно ровно в момент, когда соединение официально "устанавливалось".

(Раньше это маскировалось Багом 1: статус "connected" ставился ДО
события `track`, поэтому единственная перерисовка происходила ДО
создания audio-элемента — уничтожать было ещё нечего; а вторую
перерисовку по факту реального подключения блокировал guard
`activeCall.status !== "connected"`, который был уже `true`. Исправление
Бага 1 без исправления Бага 2 сделало бы тишину только заметнее —
чинить нужно было оба сразу.)

Исправлено разделением ответственности: `clearCallOverlayUI()` — новая
функция, убирает только визуальную карточку `#callOverlay` и таймер,
`#callRemoteAudio` не трогает; `renderCallOverlay()` теперь вызывает её
вместо полного `removeCallOverlay()`. `removeCallOverlay()` (полная
очистка, включая `#callRemoteAudio`) остался только там, где звонок
ДЕЙСТВИТЕЛЬНО завершается — внутри `cleanupCall()`. Теперь аудио-элемент
живёт от момента появления (`track`) до реального конца звонка, независимо
от того, сколько раз перерисовывался статус между этими двумя моментами.

**Не проверено на живом звонке с реальным звуком** (то же ограничение,
что и раньше — у автоматизированного браузера в этой среде нет доступа к
микрофону) — логика проверена чтением кода и последовательности событий,
не end-to-end с реальным аудио. Если после этого фикса всё ещё тихо —
следующий шаг диагностики: во время звонка в консоли браузера проверить
`activeCall.pc.connectionState` (должно быть `"connected"`) и
`document.getElementById("callRemoteAudio")` (должен существовать и
`.srcObject` не должен быть `null`) — если элемент есть, но звука всё
равно нет, дело либо в TURN/NAT (см. "[КРИТИЧНО]" выше), либо в
громкости/разрешениях устройства, не в этом коде.

## [ФИЧА] Временная защита сайта общим паролем

Проект теперь висит на настоящем домене (`lyomo.online`), но ещё не готов
для случайных посетителей — попросили закрыть буквально всё (даже
`auth.html`) одним общим логином/паролем поверх обычной системы
аккаунтов. Самый первый `app.use()`/`app.post()` в `server.js`, ДО
`cors()`, статики и всех `/api/*`-маршрутов.

Включается только через переменные окружения `SITE_AUTH_USER` +
`SITE_AUTH_PASS` — если хотя бы одна не задана, гейт вообще не
подключается (`if (SITE_AUTH_USER && SITE_AUTH_PASS) { ... }`), поведение
как раньше. Специально НЕ трогает локальный `.env` для разработки — эта
пара задаётся только в проде (Render → Environment), иначе на локальной
разработке гейт requestил бы пароль на каждый локальный запуск, что
неудобно. Сравнение логина/пароля — через `crypto.timingSafeEqual` (тот
же паттерн, что и `verifyPassword()` для обычных паролей пользователей) —
не голый `===`, чтобы не палить через timing-атаку.

Это ДВА независимых слоя: общий пароль сайта пускает к самим страницам/
API вообще, а дальше как обычно нужен свой аккаунт (`login`/`password`,
JWT) — проверено, что с верным общим паролем, но без JWT-токена,
`/api/me` всё равно 401. Один не заменяет другой.

**Не распространяется на WebSocket** (`/ws`) — не страшно: до `app.js`
(а значит и до кода, который открывает WS) всё равно не добраться без
прохождения этого же гейта на HTML/JS-страницах, так что дополнительная
защита самого WS-хендшейка не нужна.

**Когда защита будет не нужна** — просто убрать `SITE_AUTH_USER`/
`SITE_AUTH_PASS` из Environment на Render (redeploy), ничего в коде
менять не придётся.

### [БАГ-ФИКС] HTTP Basic Auth → своя форма + кука (на телефоне постоянно
### переспрашивало логин/пароль)

Первая версия была честным HTTP Basic Auth (системное окошко браузера) —
по прямой жалобе пользователя ("на телефоне постоянно просит ввести код
от сайта и логин") заменена на свою HTML-форму + подписанную куку.

**Причина**: Basic Auth целиком полагается на то, что браузер сам кэширует
заголовок `Authorization` и молча прикладывает его к каждому следующему
запросу того же origin. На мобильных (особенно iOS Safari, особенно в
PWA-режиме "на главный экран", см. раздел "PWA" выше) это ненадёжно —
именно для `fetch`/`XHR`-запросов (а это почти весь трафик приложения:
`/api/*`, WS-хендшейк) кэш авторизации у мобильных браузеров может не
применяться или сбрасываться значительно чаще, чем на десктопе — из-за
этого окошко логина/пароля выскакивало заново почти на каждое действие
вместо одного раза.

**Решение**: обычная HTML-форма на своей странице (`siteGateHtml()` в
server.js, инлайн-стили, без внешних зависимостей — ей ещё неоткуда
подгружать `styles.css`, весь гейт стоит раньше любой статики) + `POST
/site-auth` — при совпадении логина/пароля сервер ставит куку
`lomo_site_auth` на 180 дней
(`HttpOnly`, `SameSite=Lax`, `Secure` при HTTPS) со значением — HMAC-SHA256
от `SITE_AUTH_USER:SITE_AUTH_PASS` (детерминированный, не случайный на
процесс — иначе рестарт сервера на Render, см. "[КРИТИЧНО]" ниже,
разлогинивал бы всех из сайт-гейта без смены самого пароля). Дальше кука
— это ОБЫЧНАЯ кука, браузер прикладывает её сам к любому запросу того же
origin, включая `fetch`/`XHR`/WS-хендшейк, без специфичного для
Basic Auth браузерного кэша — именно это и чинит баг на мобильных.

`app.set("trust proxy", 1)` добавлен сразу после создания `app` — без
этого `req.secure` за обратным прокси Render всегда был бы `false`
(прокси терминирует HTTPS и стучится в контейнер по обычному HTTP), и
кука никогда не получала бы флаг `Secure`. Проверено вручную (временный
отдельный процесс сервера на другом порту с `SITE_AUTH_USER`/`PASS`,
не трогая основной дев-сервер и `.env`): `GET /` без куки — `401` + форма;
`POST /site-auth` с неверным паролем — `401` с сообщением об ошибке;
с верным — `302` + `Set-Cookie`; следующий `GET /` с этой кукой —
`200`, отдаёт настоящее приложение.

## [ФИЧА] Статус собеседника в личном диалоге + "Печатает..."

Раньше шапка личного диалога показывала то же "N в сети", что и у
комнат/групп (через `updateRoomPresence()`/`broadcastPresence()`) — для
чата один-на-один это бессмысленно (либо 0, либо 1). Теперь для `dm-*`
три честных состояния вместо счётчика:

- **"Читает"** — собеседник прямо сейчас держит открытым ИМЕННО этот
  диалог (его WS подключён к этой же `dm-<a>-<b>` комнате).
- **"В сети"** — собеседник подключён к приложению (любая страница — WS
  глобальный, см. раздел "Звонки"), но не в этом диалоге.
- пусто — нигде не подключён. Не "был(а) N назад" — то отдельная штука
  для списка участников комнаты (модалка "Информация о группе"), тут
  сознательно просто пусто, точное "N назад" для личного статуса не
  просили.
- **"Печатает..."** — временно перекрывает любое из состояний выше на 3
  секунды с момента последнего события набора текста, потом само
  возвращает то, что было (см. `showTypingIndicator()`/`applyDmPeerStatus()`
  в app.js — `dmPeerStatus` хранит "настоящий" статус отдельно от того,
  что сейчас в DOM, именно для этого отката).

**Сервер** (server.js): `broadcastDmPeerStatuses()` — при КАЖДОМ
подключении/отключении WS (не только у самого диалога — у любого,
потому что не знаем заранее, кого это затронет) пересчитывает статус для
ВСЕХ сейчас активных `dm-*`-комнат и шлёт `{type:"peerStatus", room,
status}` каждому участнику — причём именно статус СОБЕСЕДНИКА, не свой
собственный. ID обоих участников достаёт из самого имени комнаты
(`getDmParticipantIds()`, `dm-<a>-<b>` — id без дефисов) — отдельной
таблицы участников для DM нет и не нужно, в отличие от комнат/групп (см.
"Информация о группе" выше). `msg.type === "typing"` — обычная пересылка
всем остальным в той же комнате, ничего не хранится, троттлинг (не чаще
раза в ~2с) на клиенте, не на сервере.

**Клиент** (app.js): в общем WS-обработчике `"presence"` теперь
применяется только к НЕ-DM комнатам (там 0 не осталось: старый код одной
строкой применялся ко всем комнатам без разбора, это оставляло у DM
устаревающий счётчик 0/1). `switchRoom()` сбрасывает `dmPeerStatus` и
таймер "Печатает..." — статус per-room, старый к новому диалогу
отношения не имеет.

## [КРИТИЧНО] "Пользователь не найден" и потеря данных после перезапуска на Render

На бесплатном тарифе Render **нет Persistent Disk** (подтверждено в
дашборде: "Disks are not supported for free compute plans") — файловая
система эфемерна, весь `data/lomo.db` (SQLite, единственный источник
данных) и `uploads/` физически стираются при КАЖДОМ перезапуске
контейнера: это и сон/пробуждение free-инстанса при простое (~15 мин
неактивности), и любой redeploy. `JWT_SECRET` теперь зафиксирован в
переменных окружения Render (см. более раннюю заметку про деплой), поэтому
старые токены после рестарта проходят проверку подписи — но
`stmts.findUserById.get(payload.id)` в `requireAuth` (server.js) находит
пустую таблицу и честно отвечает 401 "Пользователь не найден". Внешне это
выглядит как "сломалась вся база" — потому что база правда каждый раз
пересоздаётся с нуля (пустые `users`/`posts`/`messages`/`chat_rooms`/
`chat_room_members` и т.д., см. `CREATE TABLE IF NOT EXISTS` в db.js).

Это же, вероятно, и причина "не удаётся сохранить аватар комнаты" — не
отдельный баг (сам код `PATCH /api/chat-rooms/:id` проверен вручную,
включая реальную загрузку файла через `/api/upload`, отрабатывает
корректно с чистого/консистентного состояния БД) — а тот же эффект:
после рестарта регистрация комнаты (`chat_rooms`) могла принадлежать уже
не существующему владельцу или потребовать повторной регистрации, пока
локальный кэш (`roomsLocal` в localStorage) всё ещё думает, что комната
знакома серверу.

**Решение не может принять агент** — это платная инфраструктурная
развилка: (а) апгрейд минимум до Starter-плана Render ($7/мес), который
включает Persistent Disks (сам диск — отдельная позиция стоимости сверху,
не включена в $7), либо (б) переезд на управляемую БД (например, Render
Postgres на бесплатном тарифе истекает через 30 дней — тоже не бесплатное
решение вдолгую), либо (в) сознательно жить с тем, что прод — временное
демо и данные могут обнуляться. Пользователь должен выбрать сам.

**Настоящее членство в комнате** — новая таблица `chat_room_members`

`wss.on("connection")` (server.js) при подключении к НЕ-DM комнате —
`INSERT OR IGNORE`, один раз на человека, `joinedAt` не обновляется
повторно. У DM (`dm-<a>-<b>`) членства нет и не нужно — ровно два
известных участника видны из самого id комнаты. Список отдаёт `GET
/api/chat-rooms/:id/members` (join с `users`), статус "в сети" — по
факту присутствия в глобальном `clients` (Set WS-подключений, тот же,
что и у `broadcastPresence()`), "был(а) N назад" — по новой колонке
`users.lastSeenAt` (обновляется в `touchLastSeen` на подключении И на
отключении WS — `wss.on("connection")`/`ws.on("close")`). Это НЕ то же
самое, что presence/live-счётчик "в сети" в шапке чата (см. раздел
"Чаты" выше) — presence ничего не хранит и живёт только пока открыт
именно этот WS, членство — постоянный список, кто вообще когда-либо
заходил в комнату.

**Честные счётчики медиа** — `roomMediaCounts()` (server.js): фото/видео
определяются по расширению `fileUrl` вложений в `messages` этой комнаты
(`MEDIA_IMAGE_EXT`/`MEDIA_VIDEO_EXT`), файлы — всё остальное с
`fileUrl`, ссылки — сообщения, чей `text` матчит `MEDIA_URL_RE`
(`https?:\/\/\S+`). Считается по ВСЕЙ истории комнаты, не только
последним 50 в `lastMessages` (кэш истории в WS специально ограничен 50,
а тут отдельный запрос по всей таблице). Сознательно без превью/галереи
для просмотра самих файлов — только числа, дешевле и было явно оговорено
с пользователем как достаточное для этого захода.

**"Покинуть"** — `POST /api/chat-rooms/:id/leave` удаляет строку из
`chat_room_members` (не трогает саму комнату/сообщения/права владельца).
Клиент (`deleteCurrentRoom()`) дёргает это best-effort ДО локальной
очистки `roomsLocal` — если запрос не прошёл, локальное удаление из
списка диалогов всё равно происходит (это лишь кэш для UI, не право
доступа). Работает и через старый пункт меню "Удалить и покинуть" (⋮), и
через новую кнопку "Покинуть" в модалке — один и тот же код.

**"⋮"-меню чата (`renderChatMenu()`) больше не содержит "Информация о
группе"** — этот пункт теперь буквально то же самое, что клик по
названию чата, дублировать смысла не было. "Управление группой" в меню
осталась (быстрый доступ без похода через модалку).

**Грабли при разработке (на будущее)**: подменю "Ещё" внутри модалки
изначально добавлялось через `actionsEl.insertAdjacentElement("afterend",
moreMenu)` — то есть СОСЕДОМ `.group-modal-actions`, а не её ребёнком.
`.group-modal-actions{position:relative}` при этом НЕ становится
offset-родителем для `.group-modal-more-menu{position:absolute}`, потому
что offset-родитель ищется среди ПРЕДКОВ элемента, а не соседей — в
итоге дропдаун позиционировался относительно `.story-viewer-
overlay{position:fixed;inset:0}` (ближайшего позиционированного предка
выше по дереву), то есть от всего экрана целиком, и оказывался у самого
низа viewport'а. Исправлено на `actionsEl.appendChild(moreMenu)` — теперь
внутри строки действий, `position:absolute` вынимает его из flex-потока,
не влияя на 4 кнопки. Урок: `position:absolute`-потомку нужен
позиционированный ПРЕДОК, не просто "который-то элемент рядом на странице".

  API, только эти 4 фиксированы), `title`, `body` (весь текст одной строкой,
  **параграфы разделены `\n`** — один пункт соглашения = одна строка; это
  же формат 1:1 с `<textarea>` в админке, без парсинга JSON туда-обратно),
  `updatedAt`.
- **Разовый посев дефолтным текстом** — `DEFAULT_TERMS` + `seedDefaultTerms()`
  (server.js, сразу после `migratePlaintextPasswords()`): если таблица
  пустая при старте сервера — заполняет её тем же текстом на 4 языках, что
  раньше был захардкожен в `TERMS_CONTENT` в app.js. После первого посева
  единственный источник правды — сама таблица; передеплой/перезапуск
  сервера НЕ перезаписывает уже отредактированный текст (проверка "таблица
  пустая", а не "всегда затирать дефолтом").
  **Грабли при разработке**: JS-комментарий ВНУТРИ template-literal-строки
  SQL (`db.exec(\`...\`)`) — если написать в нём буквально `\n` (например,
  "по одному \n на строку"), JS ещё ДО того, как SQLite увидит эту строку,
  раскрывает `\n` в настоящий перевод строки — однострочный SQL-комментарий
  `-- ...` обрывается раньше времени, и хвост комментария остаётся голым
  SQL-текстом на следующей строке (`near ','` syntax error, если после
  разрыва первым символом оказывается запятая). Ловилось на живом падении
  сервера при рестарте. Урок: внутри SQL, который сам живёт в JS-строке,
  никогда не писать `\n` как текст в комментарии — либо `\\n` (экранировать
  сам бэкслэш), либо просто переформулировать без обратного слэша.
- **`GET /api/terms`** (server.js) — **публичный**, без `requireAuth`:
  модалка соглашения на `auth.html` открывается ДО входа, во время
  регистрации, ей неоткуда взять токен. Отдаёт `{lang: {label,title,body}}`
  по всем языкам сразу.
- **`PATCH /api/admin/terms/:lang`** — `requireAuth + requireAdmin`,
  принимает `{title, body}`, 400 если язык неизвестен или поля пустые.
- **Клиент**: `openTermsModal()` (app.js, `auth.html`) больше не использует
  константу — грузит `/api/terms` **заново при каждом открытии** модалки
  (не кэширует между открытиями), чтобы правки из админки были видны сразу
  без пересборки/перезагрузки чего-либо на клиенте.
- **Админка** (`admin.html` → секция "Пользовательское соглашение",
  `initAdminTermsEditor()` в app.js) — те же вкладки RU/UA/EN/ES
  (`.tabs`/`.tab-btn`), под ними обычные `<input>` (заголовок) и
  `<textarea rows=12>` (текст, один пункт на строку — прямая подсказка в
  `placeholder`/лейбле, чтобы админ не пытался писать сплошным абзацем).
  "Сохранить" шлёт `PATCH` только для текущей открытой вкладки; статус
  ("Сохранено."/ошибка) — `.field-hint`, зелёный/красный по той же схеме,
  что и live-подсказка совпадения паролей на `auth.html`.

**Побочный фикс, найденный по пути**: `admin.html` — строка поиска по
постам (`#adminPostSearch`) всё ещё использовала класс `.media-form`,
который был удалён как "мёртвый код" в более раннем заходе (Музыка/Видео/
Книги, см. выше) — с тех пор строка поиска была неверстанной (голый инпут
и кнопка друг под другом без flex-строки). Заменено на `.media-upload-row`
(тот же класс, что уже используется в `photos.html`/`admin.html` рядом).
Урок на будущее: при удалении CSS-класса как "мёртвого" — грепать ВЕСЬ
проект по всем `*.html`, а не только по страницам, которые редактируются
в этом же заходе (в тот раз проверялись только `music.html`/`video.html`/
`books.html`, `admin.html` не заглянули).

Проверено вручную целиком: сервер поднимается и один раз засеивает 4
языка при пустой таблице (сообщение в логе); админка показывает текущий
текст для всех 4 вкладок; правка + "Сохранить" на RU даёт "Сохранено." и
реально пишется в БД (`PATCH` возвращает обновлённые поля); модалка на
`auth.html`, открытая СРАЗУ ПОСЛЕ правки (без перезапуска сервера/
перезагрузки чего-либо), показывает новый текст; текст возвращён к
исходному тем же PATCH-запросом после проверки.

**Важно для локальной разработки (не влияет на прод/Render)**: чтобы
проверить админку, пароль локального тестового аккаунта `admin` в
dev-базе (`data/lomo.db`) был переустановлен напрямую через одноразовый
Node-скрипт (тот же `hashPassword()`, что и в server.js) — если раньше
использовался другой пароль для входа под `admin` на этой машине, он
больше не действует, нужно либо взять новый, либо сменить пароль ещё раз
тем же способом. Прод/Render это не затрагивает — там своя, отдельная
база.

## [ФИЧА] "Правильная регистрация" — honeypot от ботов + живая валидация без похода на сервер

По прямому запросу пользователя после уточняющего вопроса (выбрал именно
эти два пункта из предложенных: honeypot и более строгая проверка при
вводе — email-регистрацию с SMTP и "запомнить меня" сознательно не стали
делать в этом заходе, см. предыдущий раздел про эту же форму).

**Honeypot против простых ботов** (`auth.html`/`app.js`/`server.js`):
- Поле `#regWebsite` (`name="website"`) в форме регистрации — обычный
  `<input type="text">`, уведённый за пределы экрана классом `.hp-field`
  (`position:absolute; left:-9999px`), а НЕ через `display:none`/`hidden`
  — часть простых ботов явно проверяет эти два самых очевидных признака
  перед тем как решить, заполнять поле или нет. Дополнительно
  `tabindex="-1"` (реальный человек не попадёт сюда табом) и
  `autocomplete="off"` (браузер не подставит туда что-то сам). Подпись
  `<label>` тоже есть ("Оставь это поле пустым") — на случай, если
  скринридер всё же до него доберётся, это не должно выглядеть как
  сломанное поле без подписи.
- Реальный пользователь это поле никогда не видит и не может осмысленно
  заполнить: значение всегда пустая строка. Бот, слепо проходящий по всем
  полям формы, его заполняет.
- **Сервер — единственная линия защиты, которая реально что-то решает**:
  `POST /api/register` (server.js) первым делом проверяет `website` —
  если не пусто, сразу 400 с той же по форме ошибкой, что и у обычной
  валидации ("Не удалось выполнить регистрацию"), без уточнения причины
  (чтобы не подсказывать боту, чем именно он спалился). Аккаунт в этом
  случае не создаётся вообще — проверено `curl`/`fetch` напрямую: с
  заполненным `website` — 400 и логин остаётся свободным; тот же логин
  без `website` — обычная успешная регистрация.

**Живая валидация логина и пароля при вводе, без запроса к серверу**
(`initAuthPage()` в app.js):
- `updateRegLoginHint()` — на каждый `input` в `#regLogin` проверяет
  `AUTH_LOGIN_FORMAT_RE` (тот же regex, что и раньше проверялся только на
  submit) и красит `#regLoginHint` в красный/зелёный с соответствующим
  текстом; пустое поле — нейтральная серая подсказка-плейсхолдер (та же,
  что была статичным текстом раньше).
- `updateRegPasswordLengthHint()` — аналогично для `#regPassword`, живой
  счётчик "Ещё N симв. до минимума" вместо того чтобы просто молчать до
  submit.
- Сознательно **не** проверяется живьём "логин уже занят" — это
  единственная проверка, которая требует похода на сервер, и пользователь
  явно попросил обойтись без него; уникальность логина по-прежнему
  проверяется только на submit самим `/api/register`, как и раньше.
- Обе живые подсказки — **дополнение**, а не замена: жёсткая проверка при
  `submit` (regex/длина/honeypot/чекбокс соглашения) никуда не делась и
  остаётся единственным реальным гейтом — живые подсказки лишь показывают
  результат той же проверки раньше, чем человек нажмёт кнопку.

Проверено вручную: набор невалидного логина (с пробелом/восклицательным
знаком) и короткого пароля — обе подсказки сразу красные с понятным
текстом; исправление на валидные значения — обе зеленеют; прямой
`fetch("/api/register", {..., website: "что-то"})` — 400, аккаунт не
создан; тот же запрос без `website` — 200, аккаунт создан; полный цикл
через реальный UI (клик по табу, ввод, чекбокс, submit) — успешная
регистрация и переход на ленту, как и раньше.

## [ФИЧА] Имя и фамилия при регистрации

По прямому запросу пользователя. Два новых поля в форме регистрации —
"Имя" и "Фамилия" (`#regFirstName`/`#regLastName`, в один ряд через новый
`.auth-name-row`, между honeypot-полем и логином).

**Осознанное архитектурное решение — без новых колонок в БД.** В проекте
уже есть единственное "видимое" имя пользователя — `users.displayName`
(редактируется свободным текстом на "Мой аккаунт", см. основной раздел
про `login` vs `displayName` в начале файла). Заводить рядом ОТДЕЛЬНЫЕ
`firstName`/`lastName` как самостоятельные колонки означало бы либо два
независимых, рассинхронизирующихся имени (что показывать — их или
`displayName`?), либо переделку редактирования профиля под три поля
вместо одного — сильно больше объём для того, что просят: "имя и фамилию
при регистрации". Вместо этого `POST /api/register` (server.js) на лету
склеивает `displayName = \`${firstName} ${lastName}\`` и пишет ОДИН раз
при создании аккаунта — дальше это обычный редактируемый `displayName`,
как и было; отдельно "имя" и "фамилию" после регистрации нигде не
хранит и не показывает (что и логично: реальные соцсети тоже в итоге
показывают одно полное имя, разбивка на поля нужна только один раз на
входе, чтобы гарантировать, что оба слова заполнены).

- **`NAME_FORMAT_RE`** (server.js) / **`AUTH_NAME_FORMAT_RE`** (app.js,
  синхронизированы вручную, тот же принцип, что и у `LOGIN_FORMAT_RE`) —
  `/^\p{L}[\p{L}\-' ]{0,49}$/u`: юникодная категория "буква" (`\p{L}`,
  не `[A-Za-zА-Яа-я]` — работает для любого алфавита, не только
  русского/латинского), плюс дефис и апостроф для составных имён
  ("Анна-Мария", "O'Brien"), 1–50 символов, обязательно начинается с
  буквы (не с дефиса/пробела).
- И имя, и фамилия — **обязательны**, проверяются и на клиенте (submit
  формы, `showAuthError()`, без похода на сервер — та же живая-без-сети
  идея, что и у остального этого захода), и на сервере (`/api/register`
  возвращает 400 `"Укажи имя и фамилию (только буквы, дефис или
  апостроф)"`, если пустые или не проходят regex) — сервер, как обычно
  в проекте, не доверяет клиентской проверке как единственной линии
  защиты.
- `stmts.insertUser` (server.js) расширен седьмым параметром
  (`displayName`) — теперь одна вставка сразу заводит и его, а не только
  пустую строку по умолчанию из схемы `db.js`.

Проверено вручную: реальная регистрация через UI с "Анна"/"Иванова-
Петрова" (проверка дефиса в фамилии) — `GET /api/me` после входа
подтверждает `displayName: "Анна Иванова-Петрова"`; прямой POST на
`/api/register` с пустым `firstName` и `lastName: "Test123"` (цифры) —
400 с понятной ошибкой, аккаунт не создан.

## [ФИЧА] Дата рождения при регистрации + отображение на странице пользователя

По прямому запросу пользователя, продолжение той же формы регистрации.

- **`users.birthDate`** (db.js, `ensureColumn`) — TEXT, формат "YYYY-MM-DD"
  (нативный формат `<input type="date">`), НЕ Unix-таймстамп: дата рождения
  не момент времени, часовой пояс не при чём, строка и сравнивается, и
  сортируется лексикографически так же корректно, как обычная дата.
  Пустая строка — аккаунт создан до появления этого поля (см. ниже про
  скрытие в UI).
- **Поле `#regBirthDate`** (`<input type="date">`) в форме регистрации,
  между "Имя"/"Фамилия" и "Логин".
- **Проверка возраста — не просто формальность, реально применяется** (и
  на клиенте для мгновенной обратной связи, и на сервере как единственная
  линия защиты, которой доверяем):
  - `calculateAge()`/`calculateAgeClient()` (server.js/app.js,
    продублированы, тот же принцип, что и у остальной пары клиент-сервер
    валидаций в этом заходе) — считает возраст с учётом месяца/дня, а не
    просто разницу годов (иначе человек, которому 13 лет исполнится только
    через полгода, прошёл бы проверку уже сегодня).
  - Меньше 13 лет — 400 `"LÖMO не для тех, кому меньше {N} лет"`. Это
    первое место в проекте, где утверждение "младше 13 не рекомендуется"
    из пользовательского соглашения (см. выше) реально на что-то влияет,
    а не просто текст.
  - Дата в будущем — отдельная явная ошибка ("Дата рождения не может быть
    в будущем"), не путается с "слишком молод".
  - Возраст больше 120 лет — тоже отбивается (`"Проверь дату рождения —
    похоже на опечатку"`) — лёгкая защита от опечаток в годе (например,
    "1900" вместо "2000"), не строгая бизнес-логика.
  - `BIRTH_DATE_RE` (server.js) проверяет именно ФОРМАТ строки
    ("YYYY-MM-DD") раньше, чем она попадёт в `new Date(...)` — сам
    `new Date("2024-13-45")` не бросает исключение, а тихо возвращает
    `Invalid Date`, этого недостаточно, чтобы отличить "не тот формат"
    (например, "12.03.2000") от "правильный формат, но невозможная дата".
- **Публичное отображение** — `toPublicUser()` (server.js) отдаёт
  `birthDate` всем, кто смотрит профиль пользователя (сам пользователь
  через `/api/me`, кто угодно залогиненный через
  `/api/user-by-id/:id`) — та же публичность, что уже была у `about`;
  отдельного управления видимостью ("показывать только год" / "скрыть от
  всех кроме друзей") не заводили, это осознанное упрощение, как и вся
  остальная модель "стены и профили публичны для любого залогиненного"
  (см. в начале файла).
  - **`account.html`** ("Мой аккаунт") — строка "Дата рождения:" в
    `.profile-card`, только для чтения (без поля редактирования — дата
    рождения указывается один раз при регистрации, менять её через UI
    сейчас нельзя, только напрямую в БД).
  - **`profile.html`** (просмотр чужого профиля) — та же строка, тем же
    паттерном, что и "О себе:" (скрыта через `hidden`, если `about`/
    `birthDate` пустые — не показываем пустые лейблы).
  - `formatBirthDate()` (app.js) — общий хелпер для обеих страниц:
    "YYYY-MM-DD" → "20 мая 2000 г." (`toLocaleDateString("ru-RU", {day,
    month:"long", year})`). Дата разбирается на компоненты вручную
    (`new Date(y, m-1, d)`), а НЕ через `new Date(dateStr)` напрямую —
    последнее парсит строку как UTC-полночь, и в часовых поясах западнее
    UTC результат мог бы откатиться на день назад после форматирования в
    локальном времени.

Проверено вручную: реальная регистрация с датой 20.05.2000 — и на "Мой
аккаунт", и на `profile.html?id=...` (просмотр от лица другого
пользователя, admin) корректно показывает "20 мая 2000 г."; живая
подсказка при вводе явно негодной даты (2020 год — меньше 13 лет)
красная с понятным текстом, при корректной — зелёная "Возраст подходит";
прямые POST на `/api/register` с датой в 2020 (слишком молод), в 2999
(будущее) и с мусорной строкой "not-a-date" — все три корректно отбиты
сервером каждый со своей понятной ошибкой, ни один аккаунт не создан.

## [БАГ-ФИКС] Поиск людей по имени/фамилии не работал в нижнем регистре (кириллица)

По прямому запросу пользователя — "поиск тоже поправь, чтоб можно было
найти по имени и фамилии" на всех страницах, где есть поиск человека:
`friends.html` (добавление в друзья), `chats.html` (поиск собеседника для
личного диалога) и `users.html` (админка).

**Реальная причина — не отсутствие поиска по имени (он уже был), а тихая
поломка регистронезависимости для кириллицы.** `stmts.searchUsers` в
server.js уже какое-то время как искал по `login LIKE ? OR displayName
LIKE ? OR id = ?` — то есть по имени тоже. Но `LIKE` во встроенном
`node:sqlite` (как и в обычном SQLite без ICU-расширения) регистронезависим
**только для ASCII** — `"Дмитрий" LIKE '%дмитрий%'` для SQLite ложь,
кириллица никак не участвует в его внутреннем case-folding. На практике
это означало: поиск находил "Дмитрий Кузнецов" только если ввести имя
ТОЧНО с той же капитализацией, что в `displayName` ("Дмитрий", но не
"дмитрий" и не "ДМИТРИЙ") — то есть для обычного человека, печатающего с
маленькой буквы (как все и печатают в строке поиска), поиск по имени
выглядел полностью нерабочим.

**Фикс — сравнение переехало из SQL в JS.** `matchesUserQuery(user,
query)` (server.js, новый общий хелпер) делает `.toLowerCase()` и на
логине, и на displayName, и сравнивает с `query.toLowerCase()` —
обычный JS `toLowerCase()`, в отличие от SQLite `LIKE`, кириллицу
схлопывает корректно (юникод-таблицы движка V8, а не голый ASCII).
ID сравнивается точным совпадением с исходным (не lower-cased) `query`.
- `stmts.searchUsers` (WHERE ... LIKE ...) заменён на
  `stmts.listUsersExceptSelf` (`SELECT * FROM users WHERE id <> ?`, без
  фильтра в самом запросе) — `/api/users` сам фильтрует результат через
  `matchesUserQuery()`, сортирует по логину, обрезает до 20.
- `stmts.listAllUsers` (использовался только `/api/admin/users`) — тоже

## [ФИЧА] Группы — создание в модалке (как канал в Telegram) + поиск/фильтры/категории

По прямому запросу пользователя, с консультацией у Gemini через тот же
браузерный чат (продолжение треда "UX и функционал экрана входа") — спросил
что должно быть в форме создания группы по аналогии с созданием канала в
Telegram, какие фильтры добавить в список и как классифицировать группы
внутри, чтобы фильтровать в поиске.

**Раньше**: на `groups.html` прямо наверху ВСЕГДА была видна инлайн-форма
создания (название + описание + кнопка «Создать») — занимала место
постоянно, даже когда просто хочешь посмотреть список. Под ней — плоский
список ВСЕХ групп без поиска и фильтрации. У группы был только name/
description/avatarUrl(никогда не рендерился нигде)/ownerId/createdAt.

**Ответ Gemini лёг в основу решения:**
- Форма создания — модалка с аватаром (необязательная ссылка, как и было,
  просто наконец рендерится) сверху, название (обязательно, блокирует
  кнопку «Создать» пока пусто), описание (`textarea`, `resize:none`),
  категория (`<select>`), кнопки «Отмена»/«Создать» снизу. Настройки
  приватности/короткий URL/приглашение друзей на этапе создания — прямо
  назван overkill, не делали.
- Фильтры списка: вкладки «Все группы»/«Мои группы» (состою ИЛИ владею) +
  сортировка «По популярности» (число участников, дефолт) / «Сначала
  новые».
- Классификация — **фиксированный список категорий, не свободные теги**
  (прямая рекомендация: теги потребовали бы нормализации написания,
  таблицы many-to-many и более сложного поиска ради того же результата,
  который даёт одна строковая колонка). Стартовый набор — 7 категорий:
  IT и разработка, Развлечения, Игры, Образование, Музыка, Кино, Разное
  (catch-all).

**Реализация:**
- `groups.category` (db.js, `ensureColumn`, дефолт `'other'`) — ключи
  зафиксированы в `GROUP_CATEGORY_KEYS` (server.js) и `GROUP_CATEGORY_LABELS`
  (app.js, подписи для UI); эти два места нужно держать в синхроне вручную,
  общего файла-источника у клиента с сервером в проекте нет (см. паттерн
  `LOGIN_FORMAT_RE`/`AUTH_LOGIN_FORMAT_RE` — тот же принцип).
- `POST /api/groups` — принимает `category`, подставляет `'other'`, если
  прислали что-то не из `GROUP_CATEGORY_KEYS` (сервер не доверяет
  клиентскому `<select>` как единственной защите).
- `GET /api/groups` — теперь принимает `q`/`category`/`mine`/`sort`.
  Фильтрация текстового поиска — **в JS, не SQL LIKE** (та же причина, что
  и у фикса поиска людей чуть выше: SQLite `LIKE` не схлопывает регистр
  кириллицы). Категория/`mine` — тоже JS-фильтры поверх `stmts.listGroups.all()`
  (на масштабе проекта — не тысячи групп — тащить всё и фильтровать в
  памяти проще и надёжнее, чем городить SQL под каждую комбинацию
  фильтров). `mine` — `ownerId === req.user.id OR` есть строка в
  `group_members`. Сортировка — `membersCount` убыв. (дефолт, с
  `createdAt` вторым ключом для стабильности) или `createdAt` убыв.
- Модалка создания (`openCreateGroupModal()`, app.js) — тот же паттерн
  JS-модалки, что и `openTermsModal()`: `.story-viewer-overlay` фон +
  `.contact-card-close` крестик. Аватар переиспользует уже существующий
  `.avatar-edit-row`/`.avatar-edit-preview`/`.avatar-edit-actions` с
  account.html (превью + кнопка, раскрывающая текстовое поле под ссылку) —
  отдельных классов под аватар группы заводить не пришлось. После
  успешного создания — сразу редирект на `group.html?id=<новый id>`
  (открыть только что созданную группу, как это делает Telegram с новым
  каналом), а не просто обновление списка.
- `renderGroupCard()` — карточка группы наконец получила аватар (кружок,
  буква названия как фоллбэк, тот же паттерн, что `.person-avatar`/
  `.room-avatar`) и чип категории внизу рядом со счётчиком участников.
- `group.html`/`initGroupPage()` — тоже получили аватар (было вообще
  никак не отображено, хотя `avatarUrl` существовал в БД с самого начала)
  и чип категории рядом с числом участников.
- Новые CSS-классы: `.groups-toolbar-top`/`.groups-search-row`/
  `.groups-filter-row` (лейаут панели над списком), `.chip`/`.chip.active`
  (пилюли категорий — используются и как кликабельные фильтры в
  `#groupCategoryChips`, и как статичный бейдж на карточке/странице
  группы, `.group-category-badge` только снимает `cursor:pointer` для
  второго случая), `.create-group-modal`/`.create-group-actions`.

Проверено вручную целиком: создание группы через модалку (кнопка
«Создать» задизейблена до ввода названия, аватар по ссылке показывает
превью в кружке) → редирект на страницу новой группы с аватаром/
категорией; на `groups.html` — фильтр по категории «IT и разработка»
корректно сужает список до одной группы; переключение на вкладку «Мои
группы» + сброс категории на «Все» показывает обе группы, где текущий
пользователь владелец; текстовый поиск строчными буквами («тестовая»)
находит группу по регистронезависимому совпадению с названием, комбинируясь
с уже активными вкладкой/категорией.

## [ДИЗАЙН] Кастомизация `<select>` — раньше нигде не стилизовался

По прямому запросу пользователя ("селект сортировки кастомизируй", после
добавления сортировки в Группы) — но фикс сделан ГЛОБАЛЬНО, а не только
для одного селекта: до этого `<select>` вообще нигде в проекте не имел ни
одного CSS-правила (грепнул весь styles.css перед правкой) — рендерился
голым нативным виджетом ОС (в Windows — плоский серый прямоугольник),
резко выпадающим из общего "стеклянного" стиля инпутов/карточек. Это
касалось не только нового селекта сортировки в Группах, но и уже
существовавшего select статуса книги (`want`/`reading`/`done` на карточке
в `books.html`) и select категории в модалке создания группы.

- Новое общее правило `select` (styles.css, сразу после блока `input,
  textarea`) — тот же фон/рамка/скругление, что у `input`, плюс
  `appearance:none` (убирает нативную стрелку ОС) и своя стрелка через
  `background-image` (инлайн SVG data-URI, тот же путь chevron, что и
  `chevronDown` в `ICON_PATHS`/components.js — `<select>` не может
  содержать вложенный `<svg>` как обычный элемент с иконкой, отсюда
  именно background-image, а не `icon()`). Hover/focus — тот же
  зелёный акцент, что у input/кнопок. `select option { background:
  var(--chip); color: var(--fg); }` — фон/цвет самих пунктов
  выпадающего списка (сам попап всё равно рисует ОС/браузer, не CSS, но
  Chrome/Firefox учитывают эти два свойства для содержимого).
- Отдельная стрелка для тёмной темы (`.dark select` переопределяет
  `background-image` на SVG с более светлым `stroke`) — светлая стрелка
  на тёмном фоне была бы нечитаемой.
- `.book-card-actions select` (компактный select на карточке книги) —
  правило подправлено (не переписано), чтобы не потерять место под новую
  стрелку: раньше `padding:4px 6px` не оставлял места, стрелка легла бы
  поверх текста.
- `#groupSortSelect` (Группы) и select категории в `.create-group-modal`
  отдельных правок не потребовали — общего `select` достаточно.

Проверено вручную: `groups.html` (select сортировки) и `books.html`
(select статуса на карточке книги) в обеих темах — свой фон/рамка/стрелка
вместо нативного вида ОС, текст не наезжает на стрелку в компактном
варианте на карточке книги; открытие выпадающего списка (сам попап —
ограничение платформы, стилизовать его CSS не может, только фон/цвет
пунктов).

## [ДИЗАЙН] Кастомная выпадашка `<select>` (не только закрытое состояние)

Продолжение предыдущего пункта — по прямому запросу пользователя ("выпадашку
селекта тоже кастомизируй"): раньше стилизовалось только ЗАКРЫТОЕ состояние
select (сам прямоугольник со стрелкой), а сам попап со списком опций
рисовала ОС/браузер — CSS до него не достаёт (только фон/цвет `<option>`,
не форма/тени/скругления/hover). Теперь настоящая замена: `enhanceSelect()`
(app.js) — универсальная функция, натравленная на все три select в
проекте (сортировка групп, категория в модалке создания группы, статус
книги на карточке).

**Как устроено**: настоящий `<select>` остаётся в DOM (спрятан —
`opacity:0; pointer-events:none`, всё ещё внутри `.custom-select`) и
по-прежнему единственный источник истины (`.value`, событие `"change"`) —
весь код, завязанный на select и написанный ДО этой функции (сортировка
групп, `setStatus()` у книг, отправка формы создания группы), не тронут ни
на строчку. Видимая часть — кнопка-триггер (`.custom-select-trigger`,
тот же визуальный класс, что и у самого select, см. предыдущий пункт) +
свой `<div>`-список (`.custom-select-menu`/`.custom-select-option`),
стилизованный тем же паттерном, что и `.group-modal-more-menu`.

**Две грабли, обе пойманы на живом тестировании, а не увидены заранее:**

1. **`position:fixed` — не всегда от viewport.** Первая версия считала
   координаты меню через `trigger.getBoundingClientRect()` и клала список
   как ребёнка `.custom-select` с `position:absolute`, только потом
   переехала на `position:fixed`, потому что `.create-group-modal` имеет
   `overflow-y:auto` — список категорий (7 пунктов) обрезался на второй
   строке, не помещаясь в видимую высоту скролла модалки. Но и
   `position:fixed` — не панацея: он позиционируется от viewport ТОЛЬКО
   пока ни один предок не задаёт `transform`/`filter`/`backdrop-filter`/
   `perspective` (или `will-change` с одним из них) — такой предок сам
   становится containing block для fixed-потомка. В проекте это на каждом
   шагу: hover на `.book-card`/`.group-card`/`.post-card` даёт
   `transform: translateY(-2px)`. Поймано вживую: навёл мышь на карточку
   книги (transform уже применился по hover), открыл select статуса —
   список улетел в случайную точку экрана вместо места под триггером.
   **Фикс**: `.custom-select-menu` создаётся не внутри `wrap`, а сразу
   кладётся в `document.body` (`document.body.appendChild(menu)`) — у body
   трансформов не бывает, момент открытия каждый раз пересчитывает
   координаты заново через `getBoundingClientRect()` в `position:fixed`.
2. **z-index сравнивается только внутри одного уровня вложенности.** После
   переноса меню в `body` оно стало ПРЯМЫМ соседом `.story-viewer-overlay`
   (`z-index:10000`, на нём висит модалка создания группы) — старое
   значение `z-index:1000` у меню было МЕНЬШЕ, поэтому список категорий
   рисовался ПОД самой модалкой (видна была только часть, торчащая ниже
   её нижнего края). Раньше, пока меню было вложено ВНУТРЬ модалки,
   сравнение z-index шло только среди детей самой модалки и 1000 ничему
   не проигрывал. **Фикс**: `.custom-select-menu` поднят до
   `z-index: 10001` — теперь гарантированно выше любого оверлея в проекте.
- Закрытие меню — клик вне (`document`, слушатель проверяет и `wrap`, и
  `menu`, т.к. они больше не вложены друг в друга), `Escape` не отдельно
  обрабатывается (не требовалось), скролл/ресайз окна (`window`, capture:
  true — скролл внутри модалки не всплывает обычным способом) — иначе
  список "отклеился" бы от триггера при прокрутке.
- Самоочистка: один `document`-слушатель клика на инстанс проверяет,
  жив ли ещё `wrap` в DOM — как только карточка (книги/группы) пересоздана
  при следующем рендере списка, слушатель снимает сам себя и удаляет
  осиротевший `menu` из `body` при первом же клике где угодно на странице.

Проверено вручную: список категорий в модалке создания группы теперь
целиком помещается и рисуется НАД самой модалкой (не обрезается, не
теряется под ней); выбор категории/сортировки/статуса книги закрывает
меню и реально применяет значение (список групп пересортировался, книга
перепрыгнула на вкладку "Читаю" после смены статуса); открытие select на
карточке книги ПОСЛЕ наведения мыши на неё (то есть при уже применённом
hover-transform) — список появляется на правильном месте под триггером, а
не улетает в случайную точку экрана, как было до фикса с `document.body`.

## [БАГ-ФИКС] Заголовок страницы дублировался (Группы/Книги/Видео)

Пользователь прислал скриншот `groups.html` — слово "Группы" отображалось
дважды подряд. Причина: `#headerRoot` (`renderHeader()` в components.js)

`split(" — ")` → "Группы") — это общий паттерн для всех страниц. Но у
`groups.html`/`books.html`/`video.html` от старой вёрстки остался ещё и
свой собственный `<h2>` с тем же текстом сразу под шапкой ("Группы",
"Книги", "Видео" — соответственно). Прогнал grep по всему проекту на
`<h2>` с текстом, буквально повторяющим page title, — только эти три
страницы, `friends.html`/`music.html`/`photos.html` (там `<h2>Мои
альбомы</h2>` — другой текст, не дубль) уже были без такого дублирования.

Убраны все три лишних `<h2>`. У `groups.html` заодно поправлен CSS
(`.groups-toolbar-top`) — раньше это был flex-ряд `justify-content:
space-between` между `<h2>` и кнопкой "Создать группу", теперь кнопка
одна и выровнена вправо (`justify-content: flex-end`).

## [БАГ-ФИКС] Пустые состояния были прижаты влево вместо центра страницы

Пользователь прислал скриншот `video.html` — иконка и текст "Пока нет
видео..." стояли у левого края вместо центра. Причина: `renderEmptyState()`
(app.js) кладёт `.empty-state` (сам по себе `display:flex; align-items:
center` — центрирует СВОЁ содержимое) прямо внутрь списков вроде
`.video-grid`/`.book-grid`/`.group-list`/`.photo-grid` — а они
`display:grid` с несколькими узкими колонками (`repeat(auto-fill,
minmax(200-220px, 1fr))`). Без явного `grid-column` блок становился ОДНИМ
элементом сетки и занимал ширину только первой колонки (~200px), а не всю
строку целиком — `align-items:center` честно центрировал иконку/текст, но
только внутри этой узкой колонки у левого края, а не по всей ширине
страницы.

Фикс — одна строка: `.empty-state { grid-column: 1 / -1; }` — растягивает
блок на все колонки родителя-грида. На не-grid контейнерах, где
`renderEmptyState()` тоже используется (`.wall` — лента/стена, `.person-list`
— друзья/группы, оба не grid), свойство `grid-column` ни на что не влияет,
никакой регрессии там нет.

Проверено вручную: `video.html` (пусто) и `books.html` (вкладка "Хочу
прочитать" пуста) — иконка и текст теперь по центру всей доступной ширины
страницы, а не у левого края.

## [ДИЗАЙН] Быстрая и корректная анимация перехода между страницами

По прямому запросу пользователя, с консультацией у Gemini (тот же
браузерный чат) — спросил конкретно про баланс между "просто подправить
CSS-тайминги" и "использовать нативный Cross-Document View Transitions
API"; Gemini однозначно посоветовал не считать второе оверкиллом для
pet-проекта — внедряется парой CSS-правил, не требует переписывания под
SPA, имеет полностью безболезненную деградацию для браузеров без
поддержки.

Проект многостраничный (обычная браузерная навигация через
`window.location.href`, не SPA, без роутера) — раньше единственной
"анимацией перехода" была `fadeInUp 0.4s ease` на `.sidebar`/`.app`/
`.auth-shell`, проигрывающаяся заново при КАЖДОМ переходе, включая
сайдбар, хотя его содержимое между страницами почти не меняется (только
подсветка активного пункта). При быстрой навигации по меню это ощущалось
как постоянное "моргание"/лёгкое укачивание, а не плавность.

**Слой 1 — Cross-Document View Transitions (styles.css, самый верх файла,
после блока переменных темы):**
```css
@view-transition {
  navigation: auto;
}
```
Плюс `view-transition-name: main-sidebar` на `.sidebar` и
`view-transition-name: main-header` на элемент `header` (общий для
`#headerRoot` на обычных страницах И `.auth-shell-header` на `auth.html`
— оба физически `<header>`). Совпадающее имя на старой и новой странице
говорит браузеру "это тот же объект" — он не перерисовывает такой элемент
с нуля, а плавно растворяет только то, что реально изменилось (контент).
Работает пока только в Chromium (Chrome/Edge) — это **progressive
enhancement**: в браузерах без поддержки правило молча игнорируется,
навигация остаётся обычной перезагрузкой страницы, никакого JS и ветвления
кода не потребовалось.

**Слой 2 — CSS-фоллбэк для остальных браузеров (та же `fadeInUp`, что
была, но перенастроена):**
- С `.sidebar` анимация снята полностью — он должен появляться сразу, не
  анимируясь на каждый клик по меню.
- `.app`/`.auth-shell` (сама смена контента) — `0.4s ease` →
  `0.2s cubic-bezier(0.2, 0.8, 0.2, 1)`, сдвиг снизу `20px` → `8px`.
  Gemini: в вебе всё, что дольше ~0.25s для обычной UI-навигации, начинает
  восприниматься как "тормоза"; `ease`/`ease-in-out` для ПОЯВЛЕНИЯ
  элемента не годится (ускорение в начале движения читается как рывок) —
  нужен быстрый старт с мягким торможением в конце (`ease-out`-подобная
  кривая).

**Известный побочный эффект, не баг проекта** — в консоли на КАЖДЫЙ
переход между страницами появляется `Uncaught (in promise) {code: 20,
name: "AbortError", message: "Transition was skipped"}`. Это внутренний
отказ промиса самого браузера в его собственной реализации Cross-Document
View Transition (не наш JS — приложение само нигде не вызывает
`document.startViewTransition()`, это чисто CSS-декларативный API) — на
функциональность и визуальный результат не влияет, страница каждый раз
загружается и рендерится корректно (проверено вручную). Известная
особенность этого API в Chromium на момент внедрения, не наша ошибка.

Проверено вручную: последовательные переходы между Новости → Друзья →
Чаты → Группы (в обеих темах) — сайдбар/шапка не "моргают" при переходе,
контент страницы каждый раз полностью и корректно отрисован, функциональность
(чат, поиск, фильтры) не пострадала.

## [ФИЧА] Плавающая кнопка "+" (FAB) для создания/добавления на мобильном

По прямому запросу пользователя: на телефоне основные кнопки "Создать"/
"Добавить" переехали в правый нижний угол экрана как круглая кнопка с
одним "+" — стандартный мобильный паттерн (Telegram/Gmail и т.п.), не
нужно тянуться пальцем к кнопке в самом верху длинной страницы. На
десктопе ничего не изменилось — обычная кнопка с текстом на своём месте.

**Где сделано** — везде, где на странице есть ОДНА однозначная кнопка
создания/добавления: `groups.html` (`groupCreateBtn`, "+ Создать
группу"), `books.html` (`bookAddBtn`, "+ Добавить книгу"), `photos.html`
(`albumCreateBtn`, "Создать альбом"), `music.html` (лейбл загрузки файла
"Загрузить трек"), `video.html` — но там только основная кнопка
"Загрузить видео" (файл), вторая "Добавить по ссылке" сознательно
оставлена обычной кнопкой в потоке страницы: на одной странице не может
быть двух FAB одновременно, а решать, какая из двух точек входа "главная"
— по умолчанию логично, что это загрузка своего файла, а не альтернативный
способ (ссылка).

**Осознанно НЕ сделано в `chats.html`** — по прямой просьбе пользователя
("кроме окна с диалогом и комнатой"): кнопка "+ Комната" НЕ становится
плавающей. Причина понятна и без объяснений в задаче, но по сути:
плавающий FAB поверх ленты переписки или списка диалогов перекрывал бы
сообщения/чужие комнаты — там уже есть кнопка на своём месте в тулбаре
списка диалогов, отдельный дубль не нужен. Точно так же не трогали
композер поста на стене (`index.html`/`account.html`/`group.html`,
кнопка "Опубликовать") — это submit уже открытой инлайн-формы, а не
триггер, открывающий скрытую форму создания, семантика другая.

**Как устроено (styles.css/HTML)** — новый общий класс
`.mobile-fab-trigger`, применяется прямо на существующую кнопку/`<label>`
(id и обработчики в app.js не трогали вообще, JS не менялся ни в одном
файле). Разметка кнопки-кандидата — текст оборачивается в
`<span class="btn-label">`, рядом добавляется
`<span class="fab-icon"><svg>...путь "+" из ICON_PATHS.plus...</svg></span>`.
На десктопе `.fab-icon{display:none}` — виден только текст, кнопка
выглядит как раньше. Внутри `@media (max-width:768px)` у
`.mobile-fab-trigger` — `position:fixed; right/bottom:20px`, круг 56px,
`.btn-label` скрывается, `.fab-icon` показывается. `z-index:30` — выше
обычного контента страницы, но НИЖЕ мобильного выезжающего сайдбара (50)
и его тёмной подложки (40): когда открыто меню, FAB корректно прячется
под затемнением, а не плавает поверх него.

**Особый случай — `music.html`.** Внизу экрана там может быть открыт
мини-плеер (`.mini-player`, ~60px, `position:sticky;bottom:0`) — без
поправки FAB "Загрузить трек" сидел бы прямо на нём. У лейбла-триггера
там есть свой `id="musicUploadTrigger"`, и в мобильном блоке отдельным
правилом `bottom` поднят до 90px — не зависит от того, реально ли сейчас
играет трек (это было бы сложнее: JS должен был бы то добавлять, то
убирать поправку в реальном времени вместе с появлением/исчезновением
плеера), фиксированный отступ проще и достаточно честен как компромисс.

Проверено вручную на мобильном вьюпорте (375×812) и на десктопе:
`groups.html`/`books.html`/`photos.html`/`music.html`/`video.html` —
кнопка занимает правый нижний угол, круглая, с одним "+", десктоп не
затронут; создание альбома через FAB (ввод названия в поле выше + клик
по кнопке-кружку) реально сработало — альбом "Тест FAB" создался и
появился в списке; `chats.html` на мобильном — кнопка "+ Комната"
осталась ровно там же, где и была, без изменений.

## [ДИЗАЙН] Активный вид глазика показать/скрыть пароль

По прямому запросу пользователя — глазик в полях пароля (`auth.html`)
раньше выглядел одинаково незаметно в любом состоянии: серый "muted"
что в пустом поле, что во время ввода, без разницы между "пароль скрыт"
и "пароль показан". Теперь два независимых визуальных состояния:

- **Пока печатаешь пароль** — глазик из блёклого `var(--muted)`
  становится явно видимым (`var(--fg)`), сигнализируя "кнопка сейчас
  рабочая/на что-то влияет". Чистый CSS, без JS: `.password-field:
  focus-within .password-toggle-btn` — `:focus-within` на обёртке, а не
  `:focus` на самом инпуте, потому что глазик его СОСЕД в разметке, не
  потомок.
- **Когда пароль реально показан** (`type="text"`) — глазик подсвечен
  акцентным зелёным (`var(--primary-dark)`/`var(--primary)` в тёмной
  теме) и слегка увеличен (`scale(1.1)`), причём остаётся в этом виде
  даже ПОСЛЕ потери фокуса полем — это статус "пароль сейчас виден", а
  не просто реакция на ввод. Класс `.active` ставит/снимает сам
  обработчик клика в `initAuthPage()` (app.js), синхронно с переключением
  `input.type`.

**Грабли при разработке**: `.password-toggle-btn.active` первой версией
не работал, пока в поле (или на самой кнопке) оставался фокус — после
клика по глазику браузер оставляет фокус НА КНОПКЕ, значит
`:focus-within` всё ещё истинно, а его селектор (`.password-field
:focus-within .password-toggle-btn`, 3 класса) был специфичнее, чем
`.password-toggle-btn.active` (2 класса) — при прочих равных выигрывает
БОЛЕЕ СПЕЦИФИЧНОЕ правило независимо от порядка объявления в файле, и
`:focus-within` перебивал акцентный цвет. Исправлено уравниванием
специфичности: `.password-field .password-toggle-btn.active` (тоже 3
класса) — при равной специфичности выигрывает более позднее правило по
файлу, а `.active` объявлен ниже `:focus-within`.

Проверено вручную в обеих темах: ввод текста в поле пароля — глазик
темнеет; клик по глазику — пароль показывается текстом, иконка зеленеет
и укрупняется; клик мимо поля (потеря фокуса) — зелёный цвет НЕ пропадает
(пароль всё ещё виден); повторный клик по глазику — пароль скрывается
обратно, иконка возвращается к обычному приглушённому виду.
